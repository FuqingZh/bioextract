# bioextract Domain Access Architecture

Version: v1.1
Date: 2026-08-27
Status: current

## Purpose

`bioextract` gives callers a stable, provenance-aware, and domain-correct view
of an official biological database snapshot.

Its core value is not file conversion. It hides resource-specific domain
relationships so callers do not need to understand raw release layouts,
header quirks, identifier rules, direction semantics, ontology edges, or
repeated internal joins.

Given caller-supplied local snapshot files, a resource module should expose the
database in the terms users expect: reactions and participants, ontology terms
and ancestors, proteins and annotations, pathways and members, or other
resource-owned entities and relationships.

## Independence Boundary

`bioextract` is an independent library. It does not know how a snapshot was
downloaded or which application will consume it.

It owns:

- official file formats and release layouts;
- compression and multi-file coordination;
- resource-owned entities, identifiers, and relationships;
- stable public schemas and null/obsolete/direction semantics;
- integrity and cross-file consistency checks;
- source, release, schema-version, and optional checksum provenance;
- domain-level selections that remove repeated or error-prone relationship
  traversal.

It does not own:

- downloading, mirroring, retrying, or scheduling resource acquisition;
- organization-specific resource roots or deployment paths;
- application-specific thresholds, cohorts, reports, or analysis policy;
- enrichment statistics or other scientific analyses;
- product-specific projections or presentation schemas;
- integration rules whose meaning belongs to a particular application rather
  than the source database.

Resource-owned cross-references, such as a Rhea release's mappings to ChEBI,
EC, GO, or UniProt, remain part of the resource domain. Combining independent
databases into an application-specific evidence model does not.

## Domain Contract Before Storage Strategy

The stable abstraction is the domain contract. There are exactly two storage
strategies, selected per logical product rather than treated as separate
product identities: official/native direct access when the representation is
fit, or one bioextract-owned DuckDB for a materialized logical product.

```text
caller-supplied official snapshot
                 |
                 v
        resource domain adapter
        - parse and validate
        - resolve identifiers
        - encode relationships
                 |
                 v
       stable domain views and selections
                 |
          +------+------+
          |             |
          v             v
   direct access    materialized asset
   lazy/native          DuckDB
```

Where the two strategies expose the same biological concept, their meaning and
public schema should agree even if their execution mechanisms differ.

## Direct Access Strategy

Prefer direct access when the official representation is already queryable or
cheap enough to scan for the intended operation. Examples include an indexed
SQLite database, a compact local table, or a source that maps cleanly to a lazy
reader. eggNOG, STRING, and OmniPath use this strategy.

A direct adapter must still earn its place. It should hide material domain or
format complexity such as:

- identifier normalization and alternate identifiers;
- multi-file selections;
- many-to-many expansion;
- direction or hierarchy semantics;
- stable output typing;
- unmapped-input accounting;
- release and source validation.

A wrapper that only renames `read_csv()`, `scan_parquet()`, or a simple SQL
query does not provide enough leverage to belong in `bioextract`.

### Execution convergence

Public relation nouns such as `reactions()`, `mappings()`, and `pathway_genes()`
return Polars `LazyFrame` plans. The plan is caller-owned: callers may compose
it with native Polars operations and choose `collect()`, `collect_batches()`,
or a `sink_*` operation. `bioextract` does not add a second collection API and
does not expose public `max_rows` or `batch_size` limits as a substitute for
back-pressure.

Source-backed plans use native lazy scans when the source format supports
predicate/projection pushdown. Format-specific parsers and DuckDB-backed
publications use bounded replayable Arrow batches at the adapter boundary;
they do not materialize the full relation merely to return a lazy plan.
Small lookup tables and genuinely global operations (for example ontology
transitive closure) are explicit materialization exceptions and are documented
at their owning resource boundary. A caller-visible relation remains
replayable, and one-shot publication writers retain ownership only until their
bounded write completes.

This boundary keeps storage strategy independent from query ergonomics: direct
sources, DuckDB publications, and parser-backed resources expose the same
domain-shaped lazy interface while preserving native Polars execution and
explicit caller-controlled materialization.

## Materialized Publication Strategy

Prefer materialization when the official representation is expensive or unsafe
to reinterpret repeatedly. Typical signals are:

- RDF, OBO, XML, DAT, SDF, or other domain-specific flat formats;
- multiple related files that require stable joins;
- large text inputs without useful indexes;
- repeated explode, type conversion, hierarchy traversal, or identifier
  reconciliation;
- a need to publish a validated snapshot for repeated local queries.

Every materialized logical product uses one bioextract-owned DuckDB regardless
of relation count. Parquet remains an upstream format, an internal transfer
format, or a general caller-owned interchange format; it is never a canonical
bioextract publication.

Materialization is optional. It is a performance, reuse, and delivery
mechanism; it is not the reason a resource module exists.

Stable schemas, explicit source versions, provenance, and integrity validation
are correctness requirements in both strategies, not optional performance
features.

## Query Interface Rule

Public convenience methods should encode resource-domain meaning:

- select mappings for a set of supported biological identifiers;
- traverse ontology parents or ancestors using the resource's edge semantics;
- resolve reaction participants with direction-correct roles;
- report unmatched input identifiers consistently;
- project a resource-owned relation that otherwise requires repeated internal
  joins.

Generic tabular operations do not need resource-specific wrappers. Projection,
ordinary filtering, sorting, grouping, and arbitrary SQL remain the
responsibility of Polars, DuckDB, or another native query engine exposed at the
appropriate boundary.

The goal is a deep module: a small domain interface that hides substantial
format and relationship complexity.

## Grouped Selection Execution And Cache Boundary

Grouped selection is a two-relation problem, not a request to repeat the
resource lookup independently for each group.

First normalize group labels and input IDs. Retain a group registry, including
groups with no usable IDs, and a distinct membership relation:

```text
group_id | input_id
```

Resolve the globally unique normalized `input_id` set through one set-oriented
source plan. Then join the resolved relation back to membership to fan each
match out to every owning group. Determine unmatched status at the same unique
ID grain and fan unmatched rows out through membership as well. A normalized
ID shared by several groups therefore performs one logical resolution while
each output still preserves its caller-owned `group_id`.

One resolution does not require one physical SQL statement. A backend may
chunk a bounded `IN` query, scan a source stream once against a set, or query
the several domain relations required to resolve an identifier. It must not
repeat a logical lookup solely because group membership repeats the ID.

Reusable matches, unmatched decisions, or domain anchor lineage may be cached
privately during one execution. Public noun relations return replayable lazy
frames, so cache identity is not a caller contract. Do not add process-global,
database-handle-wide, or cross-selection caches: independent selections may
carry different namespaces, policies, taxon constraints, capabilities, or
source handles.

This execution contract changes neither grouped output schemas nor publication
schemas. Resource adapters continue to own normalization, namespace rules,
biological traversal, capability validation, sorting, and the exact fields in
matched and unmatched outputs.

## Publication And Provenance

A materialized asset must identify:

- its schema version;
- the source files and their byte sizes;
- the source release when available;
- the generation time and producer version;
- optional source and asset checksums;
- enough derivation metadata to distinguish a full canonical publication from
  a selected or derived subset.

Canonical DuckDB publications store this identity in the bioextract-owned
`_bioextract` schema. No sidecar manifest is part of the canonical publication.

Biological tables live in `main`; `_bioextract` contains only:

- `metadata`;
- `source_file`;
- `table_info`;
- `column_mapping`.
- `validation_issue`.

Metadata schema v2 is the supported contract and requires all five
tables. `validation_issue` is present even
when empty; non-fatal source-integrity problems are auditable without placing
operational records in the biological schema. `_bioextract.source_file` is the
sole source inventory. Metadata v1, the redundant `bioextract.sources` key,
legacy development shapes, and unknown metadata versions are rejected.

New publications also require one resolved canonical PEP 440 producer version
from the installed `bioextract` distribution before any output or staging
mutation. Existing metadata-v2 files containing the literal package version
`"unknown"` remain readable as legacy unresolved provenance, but that value is
not compatibility or formal-delivery evidence. Formal publication candidates
must be generated by a fresh installation of the exact candidate wheel and
must inspect back to the same distribution version.

The internal schema is a bioextract product convention, not a DuckDB or SQL
reserved namespace. See the
[Materialized Dataset Contract](tidy-dataset-contract.md).

## Public Naming And Schema Boundary

Public resource handles use complete `*Database` names. Python types follow
CapWords; methods and parameters use `snake_case`. Table names, view names, and
bioextract-generated columns use singular lowercase `snake_case` without
hyphens.

The recommended import boundary is the lazy top-level database API, with one
narrow publication-inspection function:

```python
from bioextract import ChEBIDatabase, RheaDatabase, inspect_publication
```

Each database also retains its stable resource-subpackage path, for example
`from bioextract.rhea import RheaDatabase`. Resource subpackages expose only
database handles through `__all__`. The root package exposes the 11 database
handles plus `inspect_publication`; this function validates exactly one
caller-supplied DuckDB publication and does not discover publications or expose
a query interface.

Public exception categories live in `bioextract.errors`:

```python
from bioextract.errors import BioextractError, CapabilityError, IntegrityError
```

`CapabilityError` reports that an input or partial publication cannot perform
an operation. `IntegrityError` reports that source or publication integrity
cannot be established. Both inherit `BioextractError` and `RuntimeError`.
Resource-specific legacy exception names are not retained.

Selections, result records, namespaces, configuration literals, tidy dataset
classes, parsers, and writer helpers remain implementation details behind the
database methods. Their deep module paths may be used by repository-owned
tests, but are not compatibility promises and must not be presented as
package-level user imports. The only exception is the immutable publication
inspection record family, which is stable from `bioextract.publication` but is
not flattened into the root package.

Source constructors name the caller-visible logical input profile. A primary
representation uses a format-specific constructor such as
`EggNOGDatabase.from_sqlite(source)`, including when compression wraps that
representation. Explicit homogeneous profiles use names such as
`from_table_files` or `from_mapping_files`. `from_files` is retained only when
the heterogeneous named file bundle is itself the contract, as for STRING,
Reactome, OmniPath, and Rhea. Resource-local resolvers record actual resolved files
as provenance and do not infer versions from filenames or paths. The accepted
delivered rollout and compatibility boundaries are recorded in the archived
[Constructor Source Convergence Plan](../archive/20260731-v1.0-constructor-source-convergence.md).
The accepted [Runtime And Constructor Convergence Plan](../implementation-plans/20260805-v1.0-runtime-and-constructor-convergence.md)
defines the follow-up source-overlay migration and is the current authority
for the converged Rhea, KEGG metabolic, and ChEBI constructor signatures.

Fields copied one-to-one from official two-dimensional tables retain their
official headers. Fields derived from OBO, RDF, XML, SDF, headerless inputs,
joins, or prefix parsing use stable `snake_case`. Necessary collision mappings
are minimal and recorded in provenance rather than duplicated as parallel
columns.

These are bioextract compatibility rules. Within a versioned CephFS layout,
the publication convention is `tidy/data.duckdb`. Callers may choose another
filename; filenames are never schema identity, compatibility identifiers, or
machine identity.

## Resource Admission Test

A new resource or public method should satisfy all of the following:

1. It exposes a stable concept owned by the official database.
2. It removes material parsing, validation, or relationship complexity.
3. Its result has an explicit schema and provenance contract.
4. Its behavior can be verified against representative official data.
5. Removing the abstraction would force callers to reproduce meaningful
   domain logic rather than one trivial native-library operation.

If these conditions are not met, callers should use the underlying query
engine directly.

## Non-goals

`bioextract` is not:

- a downloader;
- a database mirror manager;
- a generic DataFrame wrapper;
- a cross-database application model;
- an enrichment or statistical analysis framework;
- a report-generation system.

The library may be used by any acquisition tool, notebook, workflow, service,
or application without importing or naming those systems.
Publication version identity has four independent axes: optional official
`release_version`, required content-validated `source_schema_profile`, optional
upstream-declared `source_schema_version`, and the bioextract-owned
`resource_schema_version`. Paths and timestamps never supply these values.
The installed `bioextract` package version is a separate producer-provenance
axis and never substitutes for any official or resource schema identity.
