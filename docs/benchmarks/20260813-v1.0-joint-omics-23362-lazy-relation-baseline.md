# joint_omics 23362 lazy-relation performance baseline

Version: v1.0
Date: 2026-08-13
Status: current pre-optimization decision record

## Decision

The bioextract 0.4 API migration is semantically valid, but it is not a
validated performance optimization on the bounded joint_omics workload.
Compared with bioextract 0.3, the 0.4 end-to-end median is 4.9% slower and
uses 51.4% more CPU. Its 5.3% median peak-RSS reduction is directional only
and is too variable to support a memory claim.

The pre-change relation benchmark confirms three implementation needs:

1. one selection must share expensive match and lineage work across its public
   relation frames;
2. source-backed relations need real column projection pushdown, rather than
   projecting only after a complete source frame has been constructed;
3. empty selections need to stop before downstream relation construction.

The formal 203,130,941-row idmapping workload also supplies the production
evidence that was missing from the earlier bounded fixture. It justifies
optimizing selected-ID access, but does not by itself decide whether that
should be a new public method, a pushed-down form of `scan_mapping`, or an
internal physical-plan improvement.

## End-To-End A/B Baseline

Both variants ran on the same host with the same 23,362-feature input, catalog,
four selected proteins, eight selected metabolites, Python 3.13.11, Polars
1.43.2, DuckDB 1.5.5, and PyArrow 25.0.1. Each variant had one warmup and five
measured executions. Measured executions were interleaved; no thread-limit
environment variable was set.

| median metric | bioextract 0.3 | bioextract 0.4 | 0.4 change |
| --- | ---: | ---: | ---: |
| end-to-end wall time | 12.42 s | 13.03 s | +4.9% |
| CPU time | 67.84 s | 102.70 s | +51.4% |
| peak RSS | 2,116,444 KiB | 2,003,616 KiB | -5.3% |

The component probe localizes the CPU increase to both biological layers:

| component median | 0.3 wall / CPU | 0.4 wall / CPU | interpretation |
| --- | ---: | ---: | --- |
| protein backend | 6.81 / 32.67 s | 6.71 / 52.19 s | wall flat, CPU +59.7% |
| metabolite backend | 4.06 / 29.65 s | 5.96 / 49.53 s | wall +46.8%, CPU +67.0% |

All ten executions produced the same 11-artifact contract. Parquet row counts,
column order and semantic content, JSON semantics, and rendered binary hashes
converged to one normalized manifest hash:
`95ea33817f72f26e29cd456959241b396e36a198fcac5c054640e292c424b4b1`.
The migration therefore changed execution cost without changing the observed
product result.

## Pre-Change Public-Relation Baseline

The scenario benchmark ran the released bioextract 0.4.0 implementation before
any execution-model change. It used the same four protein identifiers and the
production publications used by the downstream workload, plus KEGG compound
`C20959` to exercise a non-empty metabolic lineage. Every case reconstructs
its database handle and selection, uses only public bioextract APIs, performs
one warmup and five measured runs, and reverses case order on alternating runs.
All five output-contract hashes were stable for every case.

| case | median wall (range) | median CPU (range) | observed output |
| --- | ---: | ---: | --- |
| idmapping, one projected column | 1.598 s (1.519–1.773) | 11.677 s (10.847–11.713) | 3 rows × 1 column |
| idmapping, all columns | 1.610 s (1.461–1.838) | 11.855 s (10.582–12.293) | 3 rows × 22 columns |
| Rhea matches only | 0.475 s (0.379–0.576) | 5.808 s (5.604–7.410) | 0 matches |
| Rhea relation bundle | 1.196 s (1.078–1.381) | 24.506 s (23.774–27.578) | 0 relations, 4 unmatched |
| UniProt proteins only | 0.682 s (0.602–1.588) | 2.561 s (1.982–3.944) | 0 proteins |
| UniProt relation bundle | 1.081 s (1.004–1.202) | 5.591 s (4.387–6.907) | 0 relations, 4 unmatched |
| ChEBI matches only | 0.397 s (0.335–4.597) | 1.444 s (0.697–1.915) | 0 matches |
| ChEBI relation bundle | 1.152 s (0.967–2.916) | 4.870 s (3.413–6.431) | 0 relations, 1 unmatched |
| KEGG matches only | 0.605 s (0.548–0.690) | 4.825 s (3.470–8.457) | 1 match |
| KEGG reactions, 3 columns | 0.991 s (0.964–1.176) | 7.632 s (7.012–10.126) | 2 rows × 3 columns |
| KEGG reactions, 9 columns | 1.006 s (0.775–1.735) | 7.323 s (5.429–11.278) | 2 rows × 9 columns |
| KEGG relation bundle | 3.906 s (3.669–4.723) | 37.922 s (35.129–44.584) | 13 rows across 8 relations |

Peak RSS is deliberately absent from this table. `ru_maxrss` is
process-global and monotonic, so a value observed after one in-process case
cannot be attributed to that case. End-to-end `/usr/bin/time -v` remains the
memory acceptance measure.

## Does The Requirement Exist?

| proposed need | evidence | decision |
| --- | --- | --- |
| true projection pushdown | idmapping 1-column versus 22-column ratios are 0.993 wall and 0.985 CPU; KEGG 3-column versus 9-column ratios are 0.986 wall and 1.042 CPU | yes; current projection does not materially reduce source work |
| shared selection execution | KEGG bundle costs 6.45× the matches wall time and 7.86× its CPU; a diagnostic run rebuilt reaction lineage 6 times and unique matching 8 times | yes; highest-priority optimization |
| empty-selection short circuit | empty Rhea, UniProt, and ChEBI bundles still cost 2.52×/4.22×, 1.59×/2.18×, and 2.90×/3.37× their narrow wall/CPU cases | yes; avoid constructing relations after an empty anchor result |
| selected-ID idmapping access | 203,130,941-row publication scan spends about 11.7 CPU seconds to return 3 selected rows, and one-column projection is no cheaper than all 22 columns | workload need yes; public API shape not yet accepted |
| downstream private cache or SQL bypass | would duplicate bioextract semantics and couple joint_omics to storage internals | no |

The diagnostic counts came from one untimed, read-only probe that wrapped
internal builders only to count calls while executing public bundles. It did
not mutate implementation or form part of the timed benchmark:

- ChEBI candidate build: 3
- KEGG reaction-lineage build: 6
- KEGG unique-match build: 8
- Rhea relation execution: 4
- Rhea selected-reaction build: 2
- UniProt identifier-match build: 3

These counts explain the timing pattern; the public benchmark remains the
acceptance surface.

## Optimization And Acceptance Order

1. Make one selection execution share its normalized match set and derived
   lineage across relation frames while preserving replayability.
2. Push requested columns and selected identifiers into publication-backed
   scans, especially idmapping and KEGG deferred sources.
3. Short-circuit downstream relations after an empty normalized match set.
4. Only if those physical changes cannot meet the workload, evaluate a public
   multi-relation collection API against the existing lazy contract.

CPU median is the primary relation-level signal because duplicated parallel
work can hide behind similar wall time. Wall median is secondary. End-to-end
wall time and `/usr/bin/time -v` peak RSS remain product acceptance measures.

Do not claim an optimization unless:

- every compared case uses the same publication contract identities,
  identifiers, environment policy, warmup count, and interleaved run count;
- every relation and all 11 downstream artifacts retain their contract hashes;
- relevant relation-level CPU improves without a material wall regression;
- the joint_omics 23,362 end-to-end workload improves beyond run-to-run noise;
- no downstream private-interface or storage-SQL bypass is introduced.

The current baseline therefore accepts API and semantic compatibility only. It
does not accept an end-to-end speedup claim.
