# KEGG Mapping P3 Native Multi-file Ingestion Evaluation

Date: 2026-08-14
Status: Polars candidate evaluated and rejected; provenance-based rejection
criteria subsequently superseded, performance verdict retained

## Contract interpretation update

The later performance-plan v1.1 review corrected an over-constrained
provenance and error boundary. Source inventory no longer has to prove the
engine's exact read stream, source hashing is not part of the routine KEGG
build, and one-based line diagnostics are best effort. Those former rejection
reasons below are retained as historical evidence of what this experiment
tested; they are no longer requirements for a future native candidate.

The measured Polars verdict is unchanged. Its 1,000-organism role-only scan
used 5.37 GiB RSS for a 12.8% wall-time improvement before aggregation, so it
remains rejected independently of the superseded provenance constraints. The
next candidate is the DuckDB SQL-first path defined by the current
[performance plan](../implementation-plans/20260813-v1.0-kegg-mapping-performance-optimization-plan.md).

## Scope

This is a role-only ingestion experiment. It does not replace the publisher,
write DuckDB, or change a public API. The experiment uses the fixed first-1,000
organism scope:

```text
31998ba5b43d83ec1b906cf7078e58389befefae08862849c343bf29c8fffa85
```

The native candidate uses Polars 1.40.1 `scan_csv()` with:

- an explicit all-string role schema;
- a list of paths for each role;
- `include_file_paths="_source_path"`;
- `raise_if_empty=False` and `truncate_ragged_lines=False`;
- field trimming and per-file `unique()`; and
- an explicit path-to-organism mapping column, rather than parsing the
  organism code from a filename-derived schema identity.

The current candidate uses the existing `_read_rows()` loop with the same
selected files and per-file duplicate semantics. Both candidates produced the
same five-role row counts at 100 and 1,000 organisms.

## Measurements

| Role-only scope | Engine | Wall | Peak RSS | Rows | Result |
| --- | --- | ---: | ---: | --- | --- |
| 100 organisms | current `_read_rows()` | 4.14 s | 0.23 GiB | identical | baseline |
| 100 organisms | Polars multi-file + unique | 1.42 s | 1.37 GiB | identical | memory regression |
| 1,000 organisms | current `_read_rows()` | 23.49 s | 0.31 GiB | identical | baseline |
| 1,000 organisms | Polars multi-file + unique | 20.49 s | 5.37 GiB | identical | rejected |
| 1,000 organisms | Polars, one engine thread | 35.88 s | 4.55 GiB | identical | rejected |

The 1,000-scope role-only wall-time reduction is approximately 12.8%, below
the P1 plan's 15% acceptance threshold. This is not an end-to-end publication
comparison: aggregation and DuckDB insertion are intentionally excluded. The
native candidate's memory cost is already unacceptable before those phases are
added.

The native output contained paths for only these non-empty files:

```text
gene_ko:               1000 / 1000
gene_list:              808 / 1000
gene_pathway:           999 / 1000
ncbi_gene_conversion:   131 / 1000
uniprot_conversion:     569 / 1000
```

The omitted paths are valid zero-byte role files. The path list known before
the scan can enumerate them, but the scan result itself cannot represent them
as observed empty source records.

## Contract probes

The native scan accepts a zero-byte file when `raise_if_empty=False`, but the
file does not appear in `include_file_paths`. For malformed fixtures, Polars
raised `ColumnNotFoundError`, `SchemaError`, and `ComputeError`, respectively;
none of the messages included the source path or a one-based line number.

The scan API also exposes no callback for hashing the exact bytes consumed by
the engine. Computing SHA-256 from the paths before or after the scan would be
a second read and would not satisfy the `_bioextract.source_file` same-read
provenance rule.

## Decision

Reject direct adoption of Polars multi-file ingestion. The modest role-only
speed gain does not offset the large RSS increase. At the time of the
experiment, source-inventory and diagnostic constraints supplied additional
rejection reasons; the contract interpretation update above supersedes those
reasons without changing the performance verdict.

No production code or public contract was changed. The reproducible driver is
[`benchmark_kegg_mapping_p3.py`](../../scripts/benchmark_kegg_mapping_p3.py),
and machine-readable measurements are in
[`20260814-v1.0-kegg-mapping-p3-native-scan-evaluation.json`](20260814-v1.0-kegg-mapping-p3-native-scan-evaluation.json).

The former follow-up question was whether a bounded custom reader could retain
one-read hashes and exact diagnostics. That path is now closed. Current P3
instead evaluates DuckDB bulk role scans, reject tables, SQL validation, and
organism/key-bounded nested aggregation without a hidden fallback or public
tuning knob.
