# Cross-resource execution convergence: P3 selected lookup evidence

Date: 2026-08-14
Status: selected-query rewrite accepted; persistent index rejected by the
bounded physical gate

## UniProt idmapping

The existing production baseline records a 203,130,941-row idmapping
publication scan taking about 11.7 CPU seconds to return three selected rows;
projecting one column was essentially as expensive as projecting all 22
columns. That evidence justified a selected-ID path while preserving
`scan_mapping(taxon_ids=...)` as the full-scan relation.

The implementation now provides the accepted pre-v1 behavior on idmapping
handles:

```python
selection = database.select_ids(
    ids,
    namespace="uniprot",
    taxon_ids=[9606],
)
mapping = selection.mappings()
unmatched = selection.unmatched_ids()
```

The publication path uses a bounded parameterized predicate for small
selections and a selected-ID temporary relation for larger selections. Both
paths join inside DuckDB, apply taxon scope before output, and emit Arrow
record batches. The source path retains the native scan and pushes the
selected ID and taxon predicates into Polars. No arbitrary namespace column,
grouped idmapping selection, or per-ID query loop was introduced.

The first publication query shape used a temporary relation for every
selection. A bounded v2-clone measurement showed that this was unnecessarily
expensive for small selections: a one-ID mapping-plus-unmatched bundle took a
median 17.18 s wall / 77.50 s CPU, and 100 IDs took 4.01 s wall / 62.61 s CPU.
The implementation now uses a parameterized `IN` predicate for at most 1,000
selected IDs and keeps the temporary relation for larger sets. On the same
clone, three repetitions of the complete mapping-plus-unmatched bundle had
these medians:

| selected IDs (+ one missing sentinel) | wall | CPU | mapping rows | unmatched rows |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0.225 s | 0.340 s | 0 | 0 |
| 1 | 2.399 s | 16.71 s | 1 | 1 |
| 100 | 2.161 s | 16.26 s | 100 | 1 |
| 1,000 | 5.116 s | 39.52 s | 1,000 | 1 |

The clone contains the 203,130,941-row idmapping publication and was repaired
only in `/tmp` to metadata v2 for this contract-compatible observation. It is
not a formal publication and the benchmark is not a production-scale claim.
All mapping and unmatched output hashes were identical across repetitions. The
selected publication handle retains only a compact matched-ID anchor for
repeated `unmatched_ids()` collection; it never caches the expanded mapping
rows.

Contract and integration coverage includes empty, duplicate, repeated,
source/publication, taxon-filtered, and unmatched selections. The final
repository gate passed with 807 tests after adding P5a Rhea anchor coverage.

## KEGG reverse lookup

KEGG mapping keeps its accepted three aggregate biological tables. Reverse
selection uses one temporary selected-input relation and unnests only the
requested aggregate namespace list before joining to those selected IDs. The
existing fixed 1,000-organism development evidence and publication contract
remain the scope boundary; no fourth serving table or ART index was added.

## Physical-index decision

An ART candidate was built only on a temporary copy of the same publication.
The build took 513.1 s, raised the file from 15.73 GB to 24.62 GB (+56.5%),
and reached 12.3 GiB process RSS. DuckDB's `EXPLAIN ANALYZE` still selected a
sequential scan for an equality lookup; selected bundle medians were not
better than the parameterized query. No persistent index or acceleration
relation is therefore accepted. The absence of an index is a measured
publication decision, not a claim that every production point lookup is
already optimal.

The selected API contract is accepted, and the small-selection query rewrite
is accepted as the current physical strategy. A future publication may be
revisited only with a new fixed snapshot, a comparable cold/warm protocol,
and build/storage evidence; this slice does not alter the formal publication.
