# KEGG Mapping Publication Performance Optimization Plan

Version: v1.2
Date: 2026-08-14
Status: P3A-P3F implemented and accepted on the fixed 1,000-organism scope;
P4 focused validation and canonical CI gate passed; implementation plan
complete, release held separately
Target: KEGG mapping publication throughput with unchanged biological and
public query contracts

## Outcome First

The aggregate publication is functionally correct and memory-bounded on the
measured scoped builds, but the former Python organism-major implementation
was not fast enough for routine all-organism rebuilds. The final full-snapshot
baseline was stopped at the 10,800-second safety boundary without committing a
destination. It remains the only full build used by this optimization thread.

All further development uses the same normalized 1,000-organism scope. The
scope identity, capabilities, biological schemas, row counts, and edge
reconciliation must match before timings are comparable. A full build is not a
development benchmark and must not be rerun implicitly. A later full
publication is a separately scheduled release-readiness gate after one
candidate has been frozen.

For the recorded 2026-06 source, the fixed first-1,000 scope SHA-256 is
`31998ba5b43d83ec1b906cf7078e58389befefae08862849c343bf29c8fffa85`.
This digest identifies the small organism-code list used by the benchmark. It
is not a source-content hashing requirement.

P3 is now implemented as a DuckDB SQL-first bulk pipeline. The custom reader
existed mainly to preserve same-read hashes,
exactly-once file opens, deterministic first errors, and mandatory line
numbers. Those are execution details rather than publication outcomes and are
no longer accepted constraints.

## Stable Contracts

Optimization must preserve:

- no public `max_rows`, `batch_size`, pagination, or truncation controls;
- `from_mapping_directory()` and `from_mapping_files()` direct-root and
  overlay semantics;
- replayable native Polars `LazyFrame` relations;
- exactly the published `organism`, `gene_annotation`, and `ko_annotation`
  biological tables with the accepted nullable `List(Struct)` fields;
- direct gene-pathway observations separate from KO-derived pathways;
- the difference between an unavailable role (`null`) and an available role
  with no observation (`[]`);
- strict failure for missing required roles, malformed rows, invalid UTF-8,
  invalid identifiers, cross-organism keys, and conflicting metadata;
- logical source inventory, organism membership, scope, release identity, and
  capability provenance;
- caller responsibility for source immutability, with no `manifest.lock` or
  `biofetch` dependency;
- staged output, build-time validation, cleanup, and atomic replacement; and
- deterministic ordering inside each nested relationship list, but no
  top-level row-order promise.

## Accepted Provenance And Error Reset

The following constraints are intentionally removed or downgraded before the
new reader is adopted:

- `_bioextract.source_file` describes the resolved logical inputs selected for
  one build; it is not an audit log of physical reads performed by the engine.
- Source `bytes` is nullable when an adapter does not already know the value.
  The writer does not add `stat()` calls merely to populate provenance.
- Source SHA-256 is nullable and is recorded only when a trustworthy digest is
  already available without an extra content pass. Routine KEGG mapping builds
  do not calculate it.
- The public `include_source_hashes` writer option is removed in the
  coordinated metadata-contract slice. No compatibility alias is retained.
- Read count, open order, and exactly-once reads are performance observations,
  not publication compatibility promises.
- Exact duplicate relationship rows are idempotent input and are removed
  silently. Conflicting duplicate metadata remains fatal.
- Fatal diagnostics must identify the logical role, source path when known,
  and cause category. One-based line, byte offset, raw row, and error order are
  best-effort details rather than stable contracts.
- Immediate database and selection validation retains `CapabilityError` and
  `IntegrityError`. Execution of a returned native `LazyFrame` may surface an
  engine wrapper such as a Polars compute error with the bioextract cause.
- `from_duckdb()` performs bounded structural validation of identity,
  metadata, table inventory, schema, and capability shape. Full biological
  scans remain mandatory before publication commit and become explicit deep
  validation rather than work repeated on every reopen.

The shared metadata schema, KEGG architecture, test standard, public writer
signatures, inspection records, and affected resource writers must change as
one pre-release contract slice. Metadata v2 and the KEGG mapping publication
have not been formally released, so the change does not require a dual reader,
alias, or migration view.

## Industry Alignment

The revised direction follows the current native-engine model rather than
reimplementing a file database in Python:

| Mature pattern | Application here |
| --- | --- |
| Treat many files as one dataset or scan, while retaining the source filename as a virtual column | Pass an explicit list of paths per KEGG role to DuckDB and join the filename to a private input-file relation. |
| Separate dataset fragments/input inventory from emitted data rows | Record a resolved zero-byte file even though it emits no CSV row. |
| Use explicit schemas and dialects for stable machine-generated files | Declare all-string role schemas, tab delimiter, no header, and no schema sniffing or `union_by_name`. |
| Use bulk scan/load and set-oriented transforms instead of row-at-a-time inserts | Create private staging relations with SQL, validate with set queries, and insert final aggregate relations column-wise. |
| Capture rejects separately from valid data | Use DuckDB reject tables for bounded diagnostic evidence, then fail the build if any reject exists; rejected rows are never silently published. |
| Bound memory and spill blocking operations to disk | Configure and record DuckDB memory, thread, temp-directory, and temp-size settings for the prototype. |
| Order only order-sensitive aggregates | Use local `list(DISTINCT ... ORDER BY ...)` aggregation; do not globally sort final tables. |

Official DuckDB documentation supports explicit multi-file lists and filename
columns, reject tables with file and line evidence, bulk loading instead of
row loops, ordered and distinct aggregates, and larger-than-memory execution
through spill. Apache Arrow likewise models a dataset as independently
scannable file fragments and exposes file readahead as an execution concern,
not a result limit. Polars supports lazy multi-file CSV scans, but the measured
candidate remains rejected because its memory and wall-time evidence is poor
for this workload.

One important qualification comes directly from DuckDB's resource guidance:
complex aggregate states such as `list` may allocate memory outside the buffer
manager, so `memory_limit` alone is not a sufficient safety boundary. The
final nested aggregation must remain organism/key partitioned and prove an RSS
plateau; the plan does not replace the Python global materialization problem
with one unbounded SQL `GROUP BY`.

The application of these engine mechanisms to KEGG is a bioextract design
inference. The official references are:

- [DuckDB reading multiple files](https://duckdb.org/docs/current/data/multiple_files/overview)
- [DuckDB reading faulty CSV files](https://duckdb.org/docs/current/data/csv/reading_faulty_csv_files)
- [DuckDB data import guidance](https://duckdb.org/docs/guides/import/overview)
- [DuckDB workload tuning and spill](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads)
- [DuckDB aggregate ordering and distinctness](https://duckdb.org/docs/lts/sql/functions/aggregates)
- [DuckDB memory and temp-directory settings](https://duckdb.org/docs/stable/configuration/pragmas)
- [Apache Arrow Dataset fragments and scanners](https://arrow.apache.org/docs/cpp/api/dataset.html)
- [Polars lazy CSV scan](https://docs.pola.rs/api/python/stable/reference/api/polars.scan_csv.html)

## Fixed Benchmark Protocol

The benchmark driver supports the fixed scope through either an initial count
or, preferably, a durable organism file:

```console
pdm run python scripts/benchmark_kegg_mapping.py SOURCE OUTPUT \
  --organism-count 1000 \
  --expect-organism-scope-sha256 EXPECTED_SHA256 \
  --report REPORT.json

pdm run python scripts/benchmark_kegg_mapping.py SOURCE OUTPUT \
  --organism-file organisms.txt \
  --expect-organism-scope-sha256 EXPECTED_SHA256 \
  --report REPORT.json
```

`--organism-file` contains one normalized organism code per line. Comments
beginning with `#` and blank lines are ignored. Later experiments fail before
source parsing when the normalized scope hash drifts.

Each ordinary timing run records:

- wall and CPU seconds;
- `ru_maxrss` and sampled RSS;
- sampled open file descriptors;
- resolved source-file count;
- input bytes when measured outside the timed writer, without making byte
  counts a publication requirement;
- DuckDB version, threads, memory limit, temp directory, and temp-size limit;
- peak temporary/spill bytes and final publication bytes;
- exact three-table schemas, row counts, and capabilities;
- normalized and exploded-edge checksums; and
- reject and validation-issue counts.

The timed publisher does not hash source files. An output publication digest
may be calculated after timing as supporting artifact evidence, but embedded
generation metadata means digest equality is not the biological equality
criterion.

Profiler runs remain separate from ordinary timings:

```console
pdm run python scripts/benchmark_kegg_mapping.py SOURCE OUTPUT \
  --organism-file organisms.txt \
  --expect-organism-scope-sha256 EXPECTED_SHA256 \
  --profile-output build.prof \
  --report profiled.json
```

Profiler wall time is not reported as ordinary performance evidence.

## Current Evidence

| Scope | Wall time | Peak RSS | Result |
| --- | ---: | ---: | --- |
| 100 organisms, optimized parser candidate | 80.72 s | 1.04 GiB | completed |
| 1,000 organisms, earlier aggregate candidate | 665.69 s | 3.72 GiB | completed |
| 1,000 organisms, P1 Arrow candidate on local copy | 252.64 s | 2.88 GiB | biological evidence matches |
| 1,000 organisms, P1 Arrow candidate on CephFS | 885.99 s | 3.21 GiB | I/O variance dominates |
| 1,000 organisms, P3 DuckDB native on local copy (3 runs) | 157.53–203.19 s (median 166.63 s) | 1.92–1.96 GiB | accepted |
| 1,000 organisms, P3 DuckDB native direct CephFS (4 observations) | 165.36–251.24 s | about 2.1 GiB | I/O observation only |
| 11,782 organisms, final one-off baseline | >10,800 s | unavailable | hard-bound stop; no destination committed |

The 100-organism pre-P1 profile attributed about 39 seconds cumulatively to
organism aggregation, 19 seconds to source-row reading, 10.8 seconds to
dict-oriented frame construction, and about 2 seconds to DuckDB insertion.
The accepted P1 Arrow construction reduced Python conversion cost and is the
reference implementation, not the new target architecture.

The Polars role-only candidate read the fixed 1,000 scope in 20.49 seconds and
5.37 GiB RSS, compared with 23.49 seconds and 0.31 GiB for `_read_rows()`. Its
12.8% wall improvement was measured before aggregation and did not justify the
memory increase. The former same-read-hash and exact-line objections are now
superseded, but the measured performance verdict remains unchanged. The
durable evidence stays in the
[P3 native-scan evaluation](../benchmarks/20260814-v1.0-kegg-mapping-p3-native-scan-evaluation.md).

## Experiment Sequence

### P0: attributed measurements — complete

The exact 1,000-member scope, ordinary/profiled separation, phase timing, and
biological checksum protocol remain the baseline. Local algorithm comparisons
use repeated runs; CephFS results are treated as I/O-sensitive and require
medians when variance can hide the acceptance threshold.

### P1: reduce Python per-row work — accepted reference

Typed Arrow construction and reduced intermediate Python objects remain the
fallback implementation while P3 is evaluated. Do not spend another iteration
micro-optimizing this path before the native candidate is decided.

### P2: Python concurrency — closed

Four complete-parser workers took 204.95 seconds and 2.28 GiB on the fixed
local 100 scope, versus 82.19 seconds and 1.24 GiB for one worker. Python
object construction and the GIL outweighed overlapped file latency.

The former raw-byte-prefetch follow-up is canceled. Native scanners already
own file scheduling and readahead; a second Python scheduler would add another
buffering layer without semantic leverage. No public or private concurrency
knob is introduced by P2.

### P3A: reconcile the accepted contract reset — complete

Predecessor: P1 reference and the accepted provenance/error decision.

Affected boundaries:

- shared metadata writer, validator, source record, inspection record, and
  writer signatures;
- every resource writer forwarding `include_source_hashes`;
- KEGG mapping architecture and testing contracts;
- publication metadata migration plan and rebuild expectations; and
- benchmark assertions that currently require source bytes, hashes, exact
  read counts, per-file duplicate warnings, or deep validation on reopen.

Implementation requirements:

1. make source byte count optional and keep source digest nullable;
2. remove the public hash-computation option without an alias;
3. construct KEGG source inventory from the resolved input plan;
4. silently normalize exact duplicate relations;
5. narrow stable error assertions to category, role, path when available, and
   cause; and
6. split structural reopen validation from mandatory pre-commit deep
   validation.

Non-goals: no reader replacement, biological schema change, publication
rebuild, or formal artifact replacement in this slice.

Verification: focused shared provenance, public-signature, inspection, KEGG
parser, and publication-reopen tests. Instrumentation must prove that the
default writer performs no content read or `stat()` solely for provenance.

Acceptance: complete. Code, architecture, test standards, inspection, and
benchmark reporting now agree on one declarative source-inventory contract.

### P3B: prototype DuckDB role scans — complete

Predecessor: P3A.

Create a prototype against DuckDB 1.5.5 with one private input relation:

```text
input_file(logical_name, organism_code, role, source_path)
```

For each KEGG role:

1. pass an explicit path list to `read_csv`;
2. declare the fixed all-string schema, tab delimiter, no header, and the
   remaining dialect explicitly so no per-file sniffing is required;
3. keep `union_by_name` disabled because every role has one fixed schema;
4. retain the virtual filename and join it to `input_file` rather than deriving
   schema identity from basenames;
5. preserve zero-byte files in `input_file` even when they emit no scan rows;
6. store a bounded diagnostic sample in DuckDB reject tables and fail the
   build if any reject exists; and
7. use structured DuckDB error information when available, with failure-only
   path narrowing or targeted rereads allowed when an engine failure does not
   identify its source.

If the installed DuckDB reader cannot include a zero-byte member in a
row-producing multi-file scan, pass only scan-eligible paths to `read_csv` and
retain the zero-byte member in `input_file`. Any file-size probe needed for
that engine workaround is measured separately; it is not performed to satisfy
publication provenance and does not make `bytes` mandatory metadata.

The reject bound limits diagnostic storage only. It never makes a malformed
build valid and never truncates biological output because any reject aborts
the staged publication.

Non-goals: no final nested aggregation, no public tuning parameters, no source
hashing, and no production fallback.

Verification: compact fixtures cover zero bytes, missing files, blank lines,
wrong column counts, invalid UTF-8, more than one malformed file, and explicit
role overlays. Role-level raw and distinct row counts must match the reference.

Acceptance: complete. Fixed role scans preserve input membership and strict
failure without Python tuple-per-row parsing. Zero-byte members remain in the
input inventory, reject tables are bounded and fatal, and malformed fixtures
cannot commit a destination.

### P3C: set-oriented validation and bounded nested aggregation — complete

Predecessor: P3B.

Use one staged DuckDB connection:

1. bulk-create private normalized role relations from the native scans;
2. apply prefix, grammar, and non-empty checks with SQL and abort on any
   invalid row;
3. remove exact relationship duplicates with key-specific `DISTINCT` and
   detect conflicting metadata with grouped conflict queries;
4. pre-aggregate every many-side relation to one row per gene or KO before
   joining the roles, so no gene-by-UniProt-by-KO-by-pathway cross-product can
   form;
5. build the gene universe from the union of available organism roles;
6. emit deterministic nested values with local ordered `list` aggregation and
   explicit empty-list/null capability projection; and
7. drop every normalized staging relation before commit so the publication
   still contains exactly the accepted three biological tables.

Do not execute one release-wide unpartitioned `list` aggregation. Partition
final aggregation by organism/key using a private execution window, append
complete partitions to the final tables, and release each partition's state.
The window is an internal resource mechanism: it cannot drop rows, alter
schemas, or appear in the public API. Its candidate values and measured
effects belong in the benchmark record.

Non-goals: no persistent normalized edge tables, ART indexes, transfer Parquet
publication artifacts, or source-backed query rewrite.

Verification: bidirectional `EXCEPT ALL`, exploded-edge checksums, null/empty
fixtures, direct-versus-KO pathway separation, and conflict fixtures. Run at
least two private window values on a compact fixture and prove identical
content.

Acceptance: complete on 100 and fixed 1,000 scopes. The native writer processes
eight private organism hash windows, emits exactly the accepted three tables,
and produces identical row counts and nested-edge checksums across repeated
runs. Top-level physical row order is intentionally not a contract.

### P3D: bound DuckDB resources and cleanup — complete

Predecessor: P3C.

The prototype explicitly records and tests:

- `threads`;
- `memory_limit`;
- `temp_directory`;
- `max_temp_directory_size`;
- peak RSS, including memory outside DuckDB's buffer manager;
- peak spill/temp bytes and staged database/WAL bytes; and
- cleanup after success, parser rejects, SQL validation failure,
  interruption, and cancellation.

These are execution resource settings, not result limits. Exhaustion fails the
build and preserves the previous destination; it never returns a partial
publication. No public `memory_limit`, `threads`, or window parameter is added
until evidence demonstrates a caller decision that cannot be handled by the
repository's existing runtime/resource boundary.

Acceptance: complete for the fixed scope. DuckDB 1.5.5 uses an internal
eight-thread cap, a per-run memory bound, and a target-adjacent temporary
directory with a disk-derived maximum. Fixed 1,000 runs peaked at 1.92–1.96
GiB RSS, 19–22 descriptors, and zero spill bytes; injected failures leave no
temporary directory or candidate publication.

### P3E: end-to-end fixed-scope decision — complete

Predecessor: P3D.

1. Reconcile a compact two-organism fixture and the fixed 100-organism scope.
2. Run at least two ordinary local fixed-1,000 builds; use a third when the
   spread can change the verdict.
3. Compare the median with the 252.64-second, 2.88-GiB P1 local reference.
4. Run one bounded fixed-1,000 CephFS observation only after local acceptance;
   repeat it only when variance prevents interpretation.
5. Record full schemas, capabilities, row counts, normalized and exploded-edge
   checksums, source membership, rejects, RSS/FD series, spill bytes, output
   bytes, and cleanup evidence.

Acceptance result:

- three local runs are 157.53–203.19 s (median 166.63 s) versus the 252.64 s
  P1 reference; even the slowest is 19.6% faster;
- peak RSS is 1.92–1.96 GiB versus 2.88 GiB for the P1 local reference;
- temporary storage and open descriptors remain within their recorded bounds;
- every biological and capability check is identical; and
- no rejected or invalid input can produce a committed destination.

Role-only throughput did not satisfy this gate by itself; the decision is based
on the repeated end-to-end fixed-scope runs. Direct CephFS observations remain
I/O-sensitive and are not substituted for the local acceptance basis.

### P3F: adopt one publisher — complete

Predecessor: P3E acceptance.

The Python publication writer has been replaced by the accepted DuckDB path;
the old publication implementation and hidden fallback are removed. The
Python parser remains behind source-backed `LazyFrame` execution, with
source/publication parity tested. There is one production publisher.

The P3E gate passed on the fixed scope; the custom Arrow writer is not revived.

### P4: validate the frozen candidate — complete

After P3F:

1. run focused shared metadata, signatures, KEGG parser, contract, integration,
   reopen, tamper, and atomicity tests;
2. run the ordinary fixed-1,000 publication and reverse-selection benchmarks;
3. run `BIOEXTRACT_TEST_THREADS=1 pdm run check`;
4. update the architecture, test standards, benchmark record, and plan status;
   and
5. stop without running the complete source.

The fixed-scope acceptance evidence is recorded in
[`20260814-v1.0-kegg-mapping-p3-native-publication.md`](../benchmarks/20260814-v1.0-kegg-mapping-p3-native-publication.md)
and its machine-readable companion. `BIOEXTRACT_TEST_THREADS=1 pdm run check`
passed with 792 tests in 273.88 seconds; the final repository audit found no
remaining executable references to the removed hash option or old wide
publisher. This implementation plan is complete.

A later full build requires an explicit release-readiness decision, an offline
window projected from the fixed-scope result, sufficient stage and spill disk,
and live RSS/FD/temp monitoring. It is not part of P0-P4.

## Decision Rules

- Keep a change only when its gain exceeds benchmark noise and all biological
  evidence reconciles.
- Prefer native bulk scans and set operations over Python row loops.
- Do not confuse an internal execution window or memory budget with a row
  limit: it may change resource use but never result membership.
- Do not add normalized physical lookup tables to improve build speed; serving
  indexes remain governed by reverse-query evidence.
- Do not make top-level row order a contract. Sort only order-sensitive nested
  aggregates and explicit checksum inputs.
- Treat source membership as provenance and I/O scheduling as an engine detail.
- Treat error location as structured diagnostic evidence, not stable message
  text or deterministic scheduling behavior.
- If the fixed 1,000-organism candidate cannot reach an acceptable projected
  offline window after P3, hold release and reconsider upstream compaction or
  another ingestion engine as a new architecture decision.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| DuckDB skips faulty rows when reject storage is enabled | Query rejects before any final commit and fail on the first observed reject category. |
| Zero-byte files disappear from row-producing scans | Derive capability and source membership from `input_file`, not emitted rows. |
| `list` aggregate state exceeds the buffer-manager limit | Pre-aggregate by role and partition final aggregation by organism/key; measure process RSS, not only DuckDB's setting. |
| Normalized staging expands temporary disk | Set and record a temp-size limit, measure peak spill, and delete private relations before checkpoint. |
| One global role join creates a Cartesian product | Reduce every many-side role to one row per gene/KO before joining. |
| Native engine errors lose useful location | Require role/path/cause, use reject tables, and permit failure-only targeted diagnosis. |
| Two semantic implementations drift | Use exact source/publication parity and `EXCEPT ALL`; retain only one publication writer after acceptance. |
| CephFS variance produces a false performance verdict | Decide algorithmically on repeated local runs, then use a bounded fixed-scope CephFS observation. |
| DuckDB behavior changes with dependency upgrades | Record the installed version and settings and rerun compact contract probes after lock changes. |

## Rollback And Evidence

The provenance/error reset is an accepted contract correction independent of
whether DuckDB wins the benchmark. Before release, its code, documentation,
fixtures, and public signatures can still be reverted as one coordinated unit
if cross-resource evidence disproves it; no compatibility layer is required.

Every rejected P3 candidate retains a benchmark record with its exact input
scope, dependency versions, settings, biological reconciliation, wall time,
RSS, and temporary-storage evidence. Formal CephFS replacement, deletion of an
older publication, Git delivery, and package release remain separate actions.
