# Public API And Grouped Selection Convergence Implementation Plan

Version: v1.0
Date: 2026-07-31
Status: completed

## Purpose

This plan records the v1.0 convergence of three related contracts:

- one small, lazy public import surface centered on database handles;
- one shared grouped-selection execution model that resolves each normalized
  identifier once per selection and then restores caller groups; and
- one explicit boundary between stable package exports and internal behavior
  types.

The work changes Python API organization and query execution. It does not
change a resource publication schema, biological table, column, embedded
metadata key, resource schema version, or output container.

## Final Public API

The root package lazily exposes exactly these database handles:

```python
from bioextract import (
    ChEBIDatabase,
    EggNOGDatabase,
    GODatabase,
    InterProDatabase,
    KEGGDatabase,
    OmniPathDatabase,
    ReactomeDatabase,
    RheaDatabase,
    STRINGDatabase,
    UniProtDatabase,
    WikiPathwaysDatabase,
)
```

Importing `bioextract` alone does not initialize the resource modules.
Accessing one database class imports and caches only its owning resource
module. The corresponding resource path, such as
`from bioextract.rhea import RheaDatabase`, remains stable.

`bioextract.errors` owns the stable exception categories:

```python
from bioextract.errors import BioextractError, CapabilityError, IntegrityError
```

Resource subpackages export only their database handle. Selection classes,
writer-result records, namespace and configuration types, tidy dataset
classes, parsers, and lower-level writer helpers are implementation types.
Repository tests may import their deep modules to validate behavior, but those
paths are not compatibility promises.

## Shared Grouped-Selection Contract

Every grouped selection follows the same logical data flow:

```text
ids_by_group
    -> normalized group registry
    -> distinct (GroupId, InputId) membership
    -> globally unique normalized InputId set
    -> one set-oriented source resolution per selection
    -> membership join that restores GroupId
    -> matched and unmatched grouped outputs
```

The contract has the following consequences:

- duplicate raw IDs and distinct raw forms that normalize to the same ID are
  resolved once;
- one normalized ID may belong to multiple groups without repeated source
  resolution;
- every matching biological row is fanned out to each owning group;
- unmatched status is decided once per normalized ID and then fanned out to
  each owning group;
- duplicate membership within one group is removed;
- empty groups remain in the selection's group registry even though they
  produce no matched or unmatched identifier row;
- deterministic normalized IDs, membership rows, and outputs are sorted; and
- caches belong to one selection instance only. There is no process-global,
  database-handle-wide, or cross-selection result cache.

“One source resolution” means one set-oriented resolution plan for the unique
ID set. A backend may safely chunk an `IN` query, scan one source stream while
checking a set, or query several relations required by the domain. It must not
repeat the same logical ID lookup merely because the ID belongs to several
groups.

## Implementation Phases

### Phase 1: shared inputs and established mapping resources

The shared grouped-input builder was established as the canonical owner of
group normalization, group-registry retention, `(GroupId, InputId)`
deduplication, and deterministic ordering.

The existing efficient paths were retained:

- KEGG organism mapping materializes its mapping once and performs one
  set-oriented join;
- eggNOG queries one globally unique protein-ID set, with bounded SQLite
  chunks, then restores groups; and
- InterPro scans `protein2ipr` once against a globally unique ID set, then
  restores groups.

### Phase 2: resource adapters and DuckDB selections

Grouped selection implementations were converged for:

- ChEBI;
- Rhea;
- KEGG metabolic;
- UniProtKB;
- Reactome;
- WikiPathways;
- STRING;
- OmniPath;
- eggNOG;
- InterPro; and
- KEGG organism mapping.

Each resource keeps its own normalization rules, namespace validation,
biological relation traversal, capability checks, and output schema. Only the
execution shape is shared: unique resolution first, group fan-out second.
Selections cache reusable identifier matches or anchor lineage within the
selection when multiple extractors consume them.

### Phase 3: imports, internal types, documentation, and gates

The root and resource-package `__all__` contracts were reduced to database
handles. Generic operational exceptions moved to `bioextract.errors`.
Repository-owned tests moved internal behavior-type imports to their defining
modules without presenting those paths as user APIs.

The docstring gate was renamed from a public-class matrix to a behavior matrix.
It includes database handles and returned selection behavior, including
ChEBI, UniProt, and KEGG metabolic selections, while keeping direct observable
examples for every covered caller-facing method.

README and architecture examples now prefer top-level database imports and
document the stable resource-package alternative, public error categories,
and deep-type compatibility boundary.

## Acceptance

The completed implementation satisfies these checks:

1. Root `bioextract.__all__` contains exactly the eleven database classes.
2. Importing the root package is lazy, and a top-level database class is
   identical to the class exported by its resource package.
3. Every resource package exports exactly one database class.
4. `bioextract.errors.__all__` contains exactly the three shared exception
   categories with the documented inheritance.
5. KEGG BRITE and metabolic implementation packages expose no wildcard public
   surface.
6. Repeated IDs within and across groups, including normalization collisions,
   execute one logical lookup per normalized ID.
7. Matches and unmatched IDs restore every owning `GroupId` without leaking
   rows between groups.
8. Empty groups remain registered, and grouped outputs retain deterministic
   schemas and ordering.
9. Repeated extractors on one selection reuse the selection-owned resolution
   cache; a new selection performs its own resolution.
10. The strict behavior-docstring matrix covers database and returned
    selection behavior.
11. Focused resource tests and the repository-owned `pdm run check` gate are
    the executable completion evidence.

## Compatibility And Schema Decision

This is a deliberate pre-1.0 Python import-contract convergence. Removed
resource-specific error names and auxiliary package exports receive no aliases.
Database handle names, constructors, selection method names, returned
biological fields, publication formats, and read-only native query boundaries
remain unchanged. As a consistency correction, non-grouped UniProt selections
no longer expose an always-null `GroupId`; only `select_groups()` outputs carry
that column, matching the shared selection contract already used by the other
resources.

No Parquet footer contract, DuckDB `_bioextract` metadata contract, main-schema
table, resource schema version, or official-source schema profile changes as a
result of this plan.
