# Reactome Mapping Capability Expansion Implementation Plan

Version: v1.0
Date: 2026-08-17
Status: P1 complete — later capability slices, package release, and formal
publication replacement remain separately authorized
Target: pre-v1 Reactome `reactome-mapping-v0.2`; package release and formal
publication replacement separately authorized

## Goal

Expand `ReactomeDatabase` from the original three-file UniProt pathway MVP into
a role-aware Reactome mapping resource without turning it into a generic query
facade.

The design covers the complete v96 mapping-family inventory now present under
the caller-identified raw snapshot, while the first implementation slice is
deliberately limited to explicit support for
`UniProt2Reactome_All_Levels.txt`.

P1 must make lowest-level and all-level UniProt pathway mappings distinct at
the constructor, query, capability, provenance, and physical-table boundaries.
It must not pass an all-level file through the existing `uniprot_mapping` role
and publish it as the current `protein_pathway` relation.

This plan is implementation authority for P1 only. The later namespace,
reaction, complex/EWAS, and GMT slices describe the accepted architectural
envelope and priority order; each remains separately authorized before code is
changed.

## Decision Summary

| Concern | Accepted decision |
| --- | --- |
| Overall source model | Model every official file by identifier namespace, Reactome target, and, for pathway mappings, pathway level. Keep that role registry private. |
| P1 scope | Add explicit `UniProt2Reactome_All_Levels.txt` construction, query, selection, publication, and reopen support. |
| Lowest versus all levels | `lowest_level` and `all_levels` are separate capabilities. Existing calls continue to default to `lowest_level`; no method silently unions or changes levels. |
| All-level truth | The official `_All_Levels` file is the source capability. P1 does not synthesize it from the hierarchy when the file is absent. |
| Evidence grain | Canonical mapping relations retain rows that differ by `evidence_code`; enrichment projections deduplicate only `(reactome_pathway_id, uniprot_id)`. |
| Storage | Use one physical table per mapping role. Table presence and `_bioextract.source_file` encode capability availability; do not add a second capability metadata relation. |
| Public growth seam | Use `namespace`, `target`, and `pathway_level` as explicit selection dimensions. Do not expose the private role registry or a generic caller-supplied mapping dictionary. |
| Source identity | Add caller-declared `release_version`; never infer it from a path, filename, modification time, or adjacent manifest. |
| Publication contract | Move to `reactome-mapping-files-v2` and `reactome-mapping-v0.2`, metadata v2 only. Remove the ambiguous physical `protein_pathway` table without a compatibility view or dual write. |
| Formal delivery | Code, package release, formal v96 rebuild, catalog admission, and old-artifact cleanup are separate boundaries. P1 performs no CephFS write or formal replacement. |

### Why UniProt All Levels is P1

The all-level file adds hierarchy coverage without changing the identifier
universe:

| v96 observation | Lowest level | All levels |
| --- | ---: | ---: |
| All-species rows | 322,435 | 934,947 |
| Unique `(uniprot_id, pathway)` pairs | 317,978 | 917,206 |
| Duplicate pairs retained through distinct evidence rows | 4,457 | 17,741 |
| Human rows | 53,996 | 159,114 |
| Human unique UniProt IDs | 12,136 | 12,136 |
| Human mapped pathways | 2,331 | 2,854 |
| Human unique pairs | 49,631 | 141,715 |

For all four namespaces, the observed key set
`(source_id, reactome_pathway_id, evidence_code, species)` in the official
all-level file exactly equalled the reflexive hierarchy closure of the
lowest-level file through `ReactomePathwaysRelation.txt`:

| Namespace | Compared keys | Derived only | Official only |
| --- | ---: | ---: | ---: |
| UniProt | 934,947 | 0 | 0 |
| NCBI Gene | 780,042 | 0 | 0 |
| ChEBI | 307,067 | 0 | 0 |
| GtoP | 63,266 | 0 | 0 |

This establishes `_All_Levels` as an official materialized projection of the
same pathway relationship, not a new Reactome entity type. It also gives a
strong publication cross-check when the lowest-level, all-level, and hierarchy
roles are all supplied. It does not justify silently deriving a missing source
capability.

### Additional v96 files

| File | Observed shape | Design consequence |
| --- | --- | --- |
| `ReactomePathways.txt` | 23,498 pathways | Shared pathway metadata; not reaction metadata. |
| `ReactomePathwaysRelation.txt` | 23,612 parent-child edges | Shared pathway hierarchy and optional all-level parity check. |
| `Complex_2_Pathway_human.txt` | 28,387 rows, 16,505 complexes, 1,999 pathways, 29 top-level pathways | Separate human complex-to-pathway capability. |
| `Ewas2Pathway_human.txt` | 82,411 rows, 33,628 EWAS IDs, 2,333 pathways, 29 top-level pathways | Separate human EWAS-to-pathway capability. |
| `ReactomePathways.gmt.zip` | 2,855 pathways, 140,638 memberships, 11,963 symbols | Optional human gene-set capability, not part of the identifier mapping matrix. |

The Complex and EWAS entity IDs do not reliably encode the pathway species.
Their human scope comes from the official file contract and referenced pathway
IDs, not from the entity stable-ID prefix.

Reaction IDs in the reaction mapping files had no overlap with
`ReactomePathways.txt`. The reaction files also cover source IDs and species
not present in pathway mappings. They therefore require a separate reaction
target and cannot reuse pathway metadata or pathway hierarchy behavior.

The six-column reaction files contain event names with unescaped quote
characters. A default CSV quote parser misinterprets those records. Every
mapping-family reader, including the shared reader introduced for P1, must
parse literal TSV fields with quoting disabled and must validate the exact
six-field width.

### Upstream integrity observation

Pathway `R-SCE-9865878` occurs in the v96 mapping family but is absent from
`ReactomePathways.txt`. In the all-level relations it affects 13 UniProt rows,
13 NCBI rows, three ChEBI rows, and no GtoP rows.

Mapping rows remain authoritative observations and must not be removed by an
inner join to pathway metadata. When both mapping and pathway metadata are
published, the publisher records one warning per distinct
`(relation_name, reactome_pathway_id)` in `_bioextract.validation_issue` and
keeps every mapping row.

The local v96 pathway and hierarchy files matched their official versioned
counterparts during the bounded source check. A complete remote hash check of
`UniProt2Reactome.txt` did not finish inside the observation window, so this
plan does not claim remote-byte identity for that file; `manifest.lock` remains
the local snapshot provenance authority.

## Current Implementation Gap

The current `ReactomeDatabase` has exactly three source roles:

```text
uniprot_mapping -> UniProt2Reactome.txt
pathways        -> ReactomePathways.txt
relations       -> ReactomePathwaysRelation.txt
```

It publishes `protein_pathway`, `pathway`, and `pathway_relation` under
`reactome-mapping-files-v1` and `reactome-mapping-v0.1`.

Passing `UniProt2Reactome_All_Levels.txt` as `uniprot_mapping` happens to parse
with the existing six-column reader, but it falsely records the lowest-level
logical role and writes the ambiguous `protein_pathway` table. That is not an
accepted compatibility path.

The current formal v96 DuckDB contains 322,435 `protein_pathway`, 23,498
`pathway`, and 23,612 `pathway_relation` rows. It uses an older metadata
contract and is already rejected by the current metadata-v2 reader. P1 does
not mutate, replace, or delete that artifact.

The separately authorized `20260817-r1` formal publication release plan does
not include a Reactome v0.2 rebuild. This plan must not broaden that release's
frozen resource set.

## Accepted Capability Model

### Private mapping role

Internally, one mapping role is identified by:

```text
namespace:     uniprot | ncbi_gene | chebi | gtop
target:        pathway | reaction
pathway_level: lowest_level | all_levels | none
```

The role registry owns the official filename, source logical role, physical
table, source-ID column, target-ID column, event-name column, parser, and
schema. It is private because callers should depend on biological methods and
documented string values, not on a file-registry type.

The complete accepted registry is:

| Namespace | Target | Pathway level | Official filename | Source role and table | Source ID column |
| --- | --- | --- | --- | --- | --- |
| `uniprot` | `pathway` | `lowest_level` | `UniProt2Reactome.txt` | `uniprot_pathway_lowest_level` | `uniprot_id` |
| `uniprot` | `pathway` | `all_levels` | `UniProt2Reactome_All_Levels.txt` | `uniprot_pathway_all_level` | `uniprot_id` |
| `uniprot` | `reaction` | — | `UniProt2ReactomeReactions.txt` | `uniprot_reaction` | `uniprot_id` |
| `ncbi_gene` | `pathway` | `lowest_level` | `NCBI2Reactome.txt` | `ncbi_gene_pathway_lowest_level` | `ncbi_gene_id` |
| `ncbi_gene` | `pathway` | `all_levels` | `NCBI2Reactome_All_Levels.txt` | `ncbi_gene_pathway_all_level` | `ncbi_gene_id` |
| `ncbi_gene` | `reaction` | — | `NCBI2ReactomeReactions.txt` | `ncbi_gene_reaction` | `ncbi_gene_id` |
| `chebi` | `pathway` | `lowest_level` | `ChEBI2Reactome.txt` | `chebi_pathway_lowest_level` | `chebi_id` |
| `chebi` | `pathway` | `all_levels` | `ChEBI2Reactome_All_Levels.txt` | `chebi_pathway_all_level` | `chebi_id` |
| `chebi` | `reaction` | — | `ChEBI2ReactomeReactions.txt` | `chebi_reaction` | `chebi_id` |
| `gtop` | `pathway` | `lowest_level` | `GtoP2Reactome.txt` | `gtop_pathway_lowest_level` | `gtop_id` |
| `gtop` | `pathway` | `all_levels` | `GtoP2Reactome_All_Levels.txt` | `gtop_pathway_all_level` | `gtop_id` |
| `gtop` | `reaction` | — | `GtoP2ReactomeReactions.txt` | `gtop_reaction` | `gtop_id` |

The public value is `all_levels`, matching the official concept. Physical
table names use singular `all_level` to preserve the repository's singular
table naming convention.

### Supporting roles

| Source role and table | Official source | Columns |
| --- | --- | --- |
| `pathway` | `ReactomePathways.txt` | `reactome_pathway_id`, `pathway_name`, `species` |
| `pathway_relation` | `ReactomePathwaysRelation.txt` | `parent_reactome_pathway_id`, `child_reactome_pathway_id` |
| `complex_pathway` | `Complex_2_Pathway_human.txt` | `reactome_complex_id`, `reactome_pathway_id`, `top_level_reactome_pathway_id` |
| `ewas_pathway` | `Ewas2Pathway_human.txt` | `reactome_ewas_id`, `reactome_pathway_id`, `top_level_reactome_pathway_id` |
| `pathway_gene_set` | `ReactomePathways.gmt.zip` | `reactome_pathway_id`, `gene_symbol` |

`complex_pathway`, `ewas_pathway`, and `pathway_gene_set` are future
capabilities. Their presence in this table freezes their ownership and storage
shape; it does not authorize P1 implementation.

### Mapping table schemas

Every pathway mapping table has six string columns in this order:

```text
<namespace-specific source ID>
reactome_pathway_id
reactome_url
pathway_name
evidence_code
species
```

Every reaction mapping table has six string columns in this order:

```text
<namespace-specific source ID>
reactome_reaction_id
reactome_url
reaction_name
evidence_code
species
```

Pathway level is encoded by the source role and physical table, not repeated in
every row. No physical union table is published. A caller that deliberately
unions multiple levels or namespaces must add its own discriminator column at
that explicit composition boundary.

This per-role layout is preferred over one large normalized mapping table
because it:

- makes a publication capability decidable from metadata and catalog schemas;
- lets reopen validation inspect only bounded table metadata;
- avoids scanning a large relation to discover which mappings are present;
- prevents reaction and pathway schemas from being conflated; and
- permits partial publications without nullable target or level fields.

## P1 Public Contract

### Construction

P1 extends the existing keyword-only factory:

```python
ReactomeDatabase.from_files(
    *,
    uniprot_mapping=None,
    uniprot_all_levels=None,
    pathways=None,
    relations=None,
    release_version=None,
)
```

`uniprot_mapping` retains its current meaning: the official lowest-level
`UniProt2Reactome.txt` file. `uniprot_all_levels` exclusively means
`UniProt2Reactome_All_Levels.txt`. Neither argument accepts the other role by
filename inference.

`release_version` is optional caller-declared snapshot identity. A supplied
value is trimmed and must remain non-empty. It is embedded in publication
metadata and never inferred from a directory component, basename,
`manifest.lock`, or modification time.

At least one source role remains required. A provided path that is missing or
not a regular file fails during construction; it never means “fall back to
another role.”

A later slice may add `from_directory(source, *, release_version=None)` for
fixed-name discovery of the full matrix. P1 does not add directory discovery
or a seventeen-argument factory.

### Whole-resource relations

P1 adds one explicit raw mapping relation and extends the existing enrichment
projection:

```python
db.pathway_mappings(
    *,
    namespace="uniprot",
    pathway_level="lowest_level",
) -> pl.LazyFrame

db.pathway_genes(
    *,
    pathway_level="lowest_level",
) -> pl.LazyFrame
```

`pathway_mappings()` returns the six canonical UniProt pathway columns in
source order. `pathway_genes()` remains a UniProt enrichment projection and
returns distinct, sorted:

```text
reactome_pathway_id
uniprot_id
```

The default for both methods is `lowest_level`, preserving existing biological
behavior. Callers that want hierarchical enrichment must request
`pathway_level="all_levels"` explicitly.

The overall design reserves:

```python
db.reaction_mappings(*, namespace="uniprot") -> pl.LazyFrame
```

for a later reaction slice. P1 does not expose a method that always fails or
claim reaction capability in its accepted namespace/target values.

### Selections

P1 establishes the stable growth seam on both selection factories:

```python
db.select_ids(
    ids,
    *,
    namespace="uniprot",
    target="pathway",
    pathway_level="lowest_level",
)

db.select_groups(
    ids_by_group,
    *,
    namespace="uniprot",
    target="pathway",
    pathway_level="lowest_level",
)
```

The returned selection's existing `mappings()` and `unmatched_ids()` methods
operate on the configured capability. In P1, the only implemented namespace
and target are `uniprot` and `pathway`; both pathway levels are valid.

The selected mapping output remains:

```text
input_id
uniprot_id
reactome_pathway_id
pathway_name
evidence_code
species
reactome_url
```

Grouped output prepends `group_id`. `unmatched_ids()` retains its current
single/grouped shapes. Evidence-distinct mapping rows are retained.

The selection configuration, source role, and physical table identify the
chosen level. The relation does not add a repeated constant
`pathway_level` column. No query path can combine the two levels implicitly.

Existing calls without new keywords continue to mean UniProt, pathway,
lowest-level. Invalid string values raise `ValueError`. A valid implemented
role whose file/table is absent raises `CapabilityError`. There is no implicit
hierarchy-closure fallback when `uniprot_all_levels` is absent.

### Species behavior

`with_species()` continues to apply an exact trimmed Reactome species display
name. It filters the chosen mapping role before selection or enrichment
deduplication.

Pathway relation scoping continues to require pathway metadata and retain only
edges whose parent and child are in that species. Reaction mappings do not
participate in this hierarchy rule. Future Complex/EWAS methods use their
human-file contract and referenced pathways, not entity-ID prefixes, for
species semantics.

## Parser And Canonicalization Contract

The mapping-family parser is shared by role, not copied into twelve
file-specific readers. It must:

1. parse a literal tab separator with CSV quoting disabled;
2. assign the six role-specific string columns at parse time;
3. reject short, ragged, or extra-field records rather than truncating them;
4. retain embedded quote characters in event names;
5. reject empty source IDs, Reactome IDs, evidence codes, or species values;
6. preserve official text rather than converting identifiers across
   namespaces; and
7. normalize only exact duplicate six-column rows, never rows that differ by
   evidence code.

P1 reuses that parser for the lowest-level and all-level UniProt roles. Tests
must include an embedded-quote reaction-shaped fixture even though reaction
query support is deferred; this prevents the shared parser contract from being
implemented in a form known to fail the already inspected matrix.

`pathway_genes()` deduplicates after species filtering and projects only the
pathway/UniProt pair. Canonical mapping tables remain at evidence-row grain.

## Publication v0.2 Contract

P1 changes the Reactome publication identity to:

```text
bioextract.metadata_schema_version = 2
bioextract.source_schema_profile   = reactome-mapping-files-v2
bioextract.resource_schema_version = reactome-mapping-v0.2
```

The exact P1 source-role to table mapping is:

| Source role | Physical table |
| --- | --- |
| `uniprot_pathway_lowest_level` | `uniprot_pathway_lowest_level` |
| `uniprot_pathway_all_level` | `uniprot_pathway_all_level` |
| `pathway` | `pathway` |
| `pathway_relation` | `pathway_relation` |

`build_tidy().frames` uses these canonical role names. Redundant
`term2gene`/`term2name` frames are removed from the v0.2 tidy inventory;
`pathway_genes()` and `pathway_names()` remain the public lazy projections.
`write_duckdb()` publishes canonical relations only.

The old `protein_pathway` name is removed because it does not distinguish
lowest-level from all-level semantics and cannot scale to the accepted
namespace matrix. No view alias, dual write, metadata-v1 reader, v0.1 reader,
or automatic migration is added before v1.0.

Partial source handles remain supported. For example, a publication built only
from `uniprot_all_levels` contains exactly
`uniprot_pathway_all_level` plus the five required `_bioextract` metadata
tables. `from_duckdb()` derives capabilities from the unique source-role
inventory and requires the exact corresponding physical table set and column
schemas.

`release_version`, when supplied, is preserved through `build_tidy()`,
`write_duckdb()`, inspection, and reopen. Reopened publications cannot be
republished, and validated-file identity pinning remains unchanged.

Reactome may call the shared metadata-v2 relation writer through a focused
private publication adapter so it can supply validation issues. P1 must not
expand the generic `TidyDataset` contract solely for this resource unless a
second resource demonstrates the same reusable need.

### Cross-role validation

Validation is conditional on the roles actually present:

- every mapping role receives structural, identifier, and exact-row checks;
- when a mapping role and `pathway` are both present, missing pathway metadata
  emits a non-fatal `missing_pathway_metadata` issue without filtering rows;
- when lowest-level, all-level, and `pathway_relation` for one namespace are
  all present, compare the distinct
  `(source_id, reactome_pathway_id, evidence_code, species)` all-level keys
  with the reflexive transitive closure of the lowest-level keys;
- any derived-only or official-only closure key is fatal for publication; and
- the absence of an optional comparison role is an unavailable check, not a
  warning and not permission to synthesize a capability.

The v96 missing-pathway observation therefore produces
`validation_status=passed_with_warnings` when the affected mapping role and
pathway metadata are published together, while retaining the mapping rows.

## Compatibility And Migration

### Preserved Python behavior

- Existing `from_files(uniprot_mapping=..., pathways=..., relations=...)`
  calls remain valid.
- `pathway_genes()`, `select_ids()`, and `select_groups()` retain lowest-level
  UniProt behavior when new keywords are omitted.
- Existing selection output columns and ordering remain unchanged in P1.
- Species matching, grouped fan-out, replayable native `LazyFrame` execution,
  caller-owned read-only `connect()`, and publication identity pinning remain
  unchanged.

### Intentional pre-v1 breaks

- Reactome publication schema changes from v0.1 to v0.2.
- Source profile changes from `reactome-mapping-files-v1` to v2.
- `protein_pathway` becomes `uniprot_pathway_lowest_level`.
- `build_tidy().frames` becomes canonical-role based and drops redundant
  enrichment frames.
- v0.1 and metadata-v1 DuckDB files are not reopened by the v0.2 reader.

These are coordinated publication-contract changes. They are not hidden
behind a flag and do not create parallel stable paths.

### Formal artifact boundary

Implementation completion means the source and temporary-publication contract
passes repository validation. It does not mean the formal v96 resource is
updated.

A later formal release must:

1. use a separately authorized release candidate and an explicit
   `release_version="96"`;
2. build outside the formal resource path;
3. validate source/publication parity, exact metadata, all-level closure, the
   preserved missing-pathway rows, and read-only reopen;
4. admit the new artifact through the publication catalog's own gate;
5. stage and replace atomically; and
6. remove or archive an old artifact only under explicit cleanup authority.

If that candidate fails, remove only its identified staging output and retain
the current formal artifact. Do not “roll back” by adding a v0.1 compatibility
reader.

## Performance Evidence Gate

P1 uses native replayable Polars relations for source access and the existing
DuckDB-to-Arrow publication path. It adds no public batch, limit, cache, or
index controls.

Before adding a selected-ID index or acceleration table, record one fixed v96
workload containing:

- full lowest-level and all-level `pathway_genes()` materialization;
- one-ID and fixed 1,000-ID selections at both levels;
- source and reopened-publication output hashes;
- elapsed time, peak RSS, package versions, snapshot identity, and request
  identity.

Only a demonstrated operational miss may justify a physical acceleration
change. Any such change needs its own table/inventory and reopen-cost decision;
it is not implied by P1.

## Risks And Controls

| Risk | Control |
| --- | --- |
| All-level data is silently treated as lowest-level | Separate constructor argument, capability key, public selector, source role, table, and schema version. |
| Default CSV quote semantics corrupt reaction names | One strict mapping-family parser with quoting disabled and an embedded-quote regression fixture in P1. |
| Evidence rows disappear during enrichment deduplication | Keep canonical evidence grain; deduplicate only the explicit `pathway_genes()` pair projection. |
| Pathway metadata gaps silently remove mappings | Never inner-join canonical mappings for admission; preserve rows and record metadata-v2 warnings. |
| Capability growth creates a generic facade | Keep the registry private and public methods Reactome-domain specific. |
| A single giant mapping table makes reopen validation unbounded | One physical table per role; exact inventory derived from source roles. |
| Closure validation is mistaken for a fallback source | Gate equality only when all roles exist; missing all-level capability fails closed. |
| v0.2 code is confused with a formal release | Separate package, formal build, catalog, atomic replacement, and cleanup authority. |
| Current user-owned release work is broadened | Do not alter the frozen `20260817-r1` resource list or reuse its staging outputs. |

## Completion Criteria

P1 is complete only when:

- constructor, relation, selection, publication, and reopen contracts all
  distinguish lowest-level from all-level UniProt mappings;
- default Python behavior remains lowest-level;
- canonical mapping tables preserve evidence rows and enrichment projections
  produce distinct pairs;
- v0.2 partial and combined publications have exact source/table capability
  inventories and no `protein_pathway` relation;
- missing pathway metadata is observable without row loss;
- the compact source/publication parity suite and bounded v96 smoke pass;
- public signatures, architecture, testing standard, README examples, and
  docstrings agree;
- the full repository gate passes; and
- the handoff states explicitly that formal v96 publication replacement was
  not performed.

Completion of P1 does not imply completion of P2–P4, a package release, a
formal CephFS publication, catalog activation, downstream migration, or old
artifact deletion.
