# Publication Metadata v2 Source Inventory Migration Plan

Version: v1.2
Date: 2026-08-14
Status: declarative-provenance revision implemented; canonical gate passed;
release remains separate
Target: shared prerequisite for the KEGG mapping aggregate publication

## Goal

Make `_bioextract.source_file` the single authoritative source inventory for
every DuckDB publication. Metadata v2 removes the duplicated
`bioextract.sources` JSON value and lets large multi-file publishers record
source provenance without a second JSON representation.

This is a cross-resource publication-contract migration. It is intentionally
separate from KEGG parsing and biological-schema work so that the shared
metadata boundary can be reviewed, tested, and accepted independently.

## Problem And Evidence

Metadata v1 stores the same inventory twice:

- a JSON array in `_bioextract.metadata["bioextract.sources"]`; and
- normalized rows in `_bioextract.source_file`.

That duplication was useful when publications could be Parquet-only and needed
footer metadata. Canonical bioextract publications are now DuckDB-only, and
`_bioextract.source_file` is already required. Keeping both representations
adds reconciliation logic, makes inspection depend on redundant state, and
forces a large publisher to retain or reconstruct a complete Python inventory.

The accepted KEGG mapping directory profile contains tens of thousands of
small files. A source-row table is suitable for that cardinality; a second
large JSON value is not. Resource adapters produce the inventory from the files
they actually resolve; the shared publication layer does not crawl source
directories or reconstruct inventory from a sidecar.

## Decision Summary

| Concern | Metadata v2 decision |
| --- | --- |
| Inventory authority | `_bioextract.source_file` is the only source-file inventory. |
| Removed key | `bioextract.sources` is neither written nor accepted. |
| Metadata version | `bioextract.metadata_schema_version` is exactly `"2"`. |
| Source discovery | Resource adapters resolve their own files; the shared writer does not crawl directories. |
| Recording | The resource adapter supplies one source record for each file resolved into the build input plan. |
| Byte count | `bytes` is an optional adapter observation; the shared writer never stats a path to require it. |
| Hash | Optional SHA-256 is stored only when an adapter already has a trustworthy digest without an extra content pass. |
| Snapshot isolation | Not provided. The caller must not mutate inputs during execution. |
| Sidecars | No sidecar manifest is introduced. |
| Upstream tools | No executable code, public API, or publication metadata reads, probes, or models biofetch artifacts such as `manifest.lock`. |
| Compatibility | Metadata v1 publications are rejected; maintained publications must be rebuilt. |
| Rollout | One cross-resource change precedes the KEGG mapping change; one package release follows both. |

## Scope

### In scope

- shared metadata writer, validator, and publication inspection behavior;
- all resource-specific publication validators that currently require
  `bioextract.sources` or metadata schema v1;
- insertion into `_bioextract.source_file` from fixed resource-owned records;
- optional source byte-count and checksum observations owned by each resource
  adapter;
- contract, integration, inspection, tamper, and smoke-test updates;
- architecture, testing, and migration documentation;
- rebuild planning for all maintained DuckDB publications.

### Out of scope

- KEGG mapping parsers, schemas, organism discovery, or domain methods;
- downloading, mirroring, release discovery, or biofetch integration;
- a publication catalog or sidecar manifest;
- filesystem snapshotting, directory locking, or whole-root drift detection;
- automatic migration or in-place rewriting of metadata v1 publications;
- rebuilding or replacing formal CephFS artifacts without separate authority;
- package publication.

## Metadata v2 Contract

Biological relations remain in `main`. Metadata v2 retains exactly these five
bioextract-owned tables:

```text
_bioextract.metadata
_bioextract.source_file
_bioextract.table_info
_bioextract.column_mapping
_bioextract.validation_issue
```

The `source_file` schema remains:

| Column | Type | Contract |
| --- | --- | --- |
| `logical_name` | `VARCHAR PRIMARY KEY` | Resource-owned stable role identity within one publication. |
| `display_path` | `VARCHAR NOT NULL` | Human-readable resolved source path; not schema or release identity. |
| `bytes` | `UBIGINT NULL` | Observed source size when already known; `NULL` otherwise. |
| `media_type` | `VARCHAR NOT NULL` | Resource-declared media type. |
| `sha256` | `VARCHAR NULL` | Lowercase source digest when already available without a provenance-only read. |

`_bioextract.metadata` must contain the existing canonical identity and
validation keys, with these changes:

- `bioextract.metadata_schema_version` is `"2"`;
- `bioextract.sources` is forbidden;
- release and source-schema identity remain caller- or official-metadata-owned
  and are never inferred from paths, basenames, timestamps, or modification
  times.

Missing canonical keys and unknown metadata schema versions continue to fail
validation according to the shared contract. Resource-specific metadata remains
allowed and is validated by its owning resource.

## Source Recording Boundary

The shared layer owns the table format and insertion mechanics. Each resource
adapter owns:

- which files are part of one logical source profile;
- the stable `logical_name` assigned to each file;
- media types and resource-specific capability semantics; and
- parsing and content-integrity rules.

Source recording is declarative:

```text
resolve build input
  -> assign logical name, display path, and media type
  -> attach byte count or digest only when already known
  -> execute the parser or native scanner
  -> publish the resolved source record with the validated result
```

The shared writer performs no `stat()`, directory inventory walk, or checksum
pass. It persists the records supplied by the resource adapter. An
adapter may retain a byte count or digest it obtains naturally, but metadata v2
does not require native scanners to expose their read streams and does not
provide a public option that triggers hashing. Read count, open order, and the
physical buffering strategy are execution observations rather than provenance
compatibility promises.

For a failed or canceled publication, source rows exist only in the unpublished
staging database and are removed with that stage. No partial inventory becomes
visible at the destination.

## Consistency And Ownership

Metadata v2 does not claim snapshot isolation. A source-backed handle is a live,
replayable description of caller-supplied local files. Each execution opens the
files it needs and observes their current contents.

The caller owns source immutability for the duration of one execution.
bioextract owns:

- accepting the resource adapter's resolved inventory without re-reading or
  re-statting its path;
- validating the content presented by the parser or native scanner;
- closing owned resources on success, failure, cancellation, and early stop;
  and
- keeping a prior destination intact until the staged publication validates.

There is no whole-directory freeze, before/after directory comparison, or
attempt to detect files added outside the actual resource discovery contract.
This avoids pretending that ordinary filesystem traversal provides a database
snapshot.

## Compatibility And Migration

This is an intentional pre-v1 publication break:

- metadata v1 readers and writers are removed together;
- no dual-write `bioextract.sources` key is retained;
- no automatic v1-to-v2 migration or compatibility view is added;
- every maintained formal publication must be rebuilt with the package that
  implements metadata v2;
- source/publication parity tests must use v2 fixtures after the migration.

The v1.1 nullable-byte and no-hash-option correction is made before any formal
metadata-v2 release. It amends v2 in place rather than introducing a temporary
v3 or a dual reader.

The Python domain API does not change merely because the metadata version
changes. A resource may have an independent API or biological-schema migration,
such as the KEGG mapping plan, but that change is reviewed separately.

Formal artifact replacement remains an explicit delivery operation. Merging
this plan's implementation does not authorize CephFS writes, deletion of v1
artifacts, or package publication.

## Affected Components

Expected shared surfaces:

- `src/bioextract/_publication.py` — version, writer, validator, atomic staging,
  source-row insertion, and redundant-JSON removal;
- `src/bioextract/publication.py` — `inspect_publication()` metadata-v2 readback;
- `src/bioextract/_tidy.py` — source-recording handoff for generic publishers;
- resource-specific validators and custom writers under `src/bioextract/`,
  including custom Rhea and KEGG metabolic publication paths;
- contract tests under `tests/contract/publication/` and
  `tests/contract/resources/`;
- integration inspection and source-to-publication tests;
- external-publication smoke validation;
- shared architecture and testing documents.

The implementation should first inventory every direct comparison with
metadata version `"1"` and every read or write of `bioextract.sources`. That
inventory is an acceptance artifact, not a permanent compatibility layer.

## Implementation Slices

### Slice M0: freeze the v2 contract and migration inventory

Predecessors: none.

Deliverables:

- exact metadata key set and `source_file` schema fixtures;
- complete inventory of shared and resource-local v1 assumptions;
- maintained-publication rebuild inventory;
- resolved source-record handoff proven against empty and non-empty
  inventories.

Non-goals: no resource parser or biological schema changes.

Verification:

- contract fixtures reject missing canonical keys, unknown metadata schema
  versions, duplicate source rows, and v1-only inventory state;
- the shared writer persists nullable adapter-supplied byte counts and digests
  without path access.

Acceptance: the migration surface is complete enough that no resource can
silently keep writing or accepting metadata v1.

### Slice M1: implement the shared writer and validator

Predecessor: M0.

Deliverables:

- metadata version `"2"`;
- removal of `bioextract.sources` generation and reconciliation;
- normalized `source_file` insertion from fixed resource records;
- no writer-side path stat, hashing, or JSON reconstruction;
- atomic cleanup for parser errors, cancellation, and destination replacement.

Non-goals: no generic directory crawler and no public batch-size option.

Verification:

- writer/readback tests for zero, one, and many source records;
- null and supplied digest/byte-count round-trip;
- tamper tests for table rows and metadata;
- old destination preservation after injected failures.

Acceptance: one validated v2 publication can be written, closed, reopened
read-only, and inspected without any redundant JSON inventory.

### Slice M2: migrate generic and custom resource publishers

Predecessor: M1.

Deliverables:

- all maintained resources write and validate v2;
- resource-specific custom writers use the shared v2 contract;
- all publication fixtures and inspection expectations are rebuilt;
- no shared or resource publication writer performs a path probe or content
  pass solely for provenance; and
- public `include_source_hashes` writer parameters are removed without aliases.

Non-goals: no unrelated resource API migrations.

Verification:

- focused resource build/reopen/query tests;
- repository search finds no executable v1 acceptance or
  `bioextract.sources` dependency;
- nullable byte/hash observations reconcile inspection rows with
  adapter-supplied records.

Acceptance: all maintained resource paths use one metadata contract.

### Slice M3: document and gate the rebuild

Predecessor: M2.

Deliverables:

- current shared architecture and test-standard updates;
- explicit rebuild list and artifact compatibility note;
- candidate-package validation instructions;
- handoff for separately authorized formal publication replacement.

Verification:

```console
BIOEXTRACT_TEST_THREADS=1 pdm run check
```

Acceptance: the code, fixtures, inspection API, documentation, and rebuild
inventory agree on metadata v2, and no release or CephFS replacement is implied.

## Verification Matrix

| Contract | Required evidence |
| --- | --- |
| Single inventory | No writer or reader emits or requires `bioextract.sources`. |
| Exact version | v2 opens; v1, missing, and unknown versions fail explicitly. |
| Source fidelity | Null or adapter-supplied bytes and SHA-256 round-trip exactly without proving engine I/O history. |
| Shared-layer isolation | Instrumented fixtures show the shared writer never opens or stats source paths. |
| Scale | Tens of thousands of source rows insert without a complete JSON value or unbounded Python inventory. |
| Atomicity | Failure or cancellation removes staging and preserves the old target. |
| Inspection | `inspect_publication()` returns the normalized source inventory from `source_file`. |
| Tamper detection | Missing, duplicate, malformed, and inconsistent source rows are rejected. |
| Cross-resource | Every maintained custom and generic publisher passes build/reopen/query tests. |
| Independence | Tests and executable code contain no dependency on biofetch or `manifest.lock`. |

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| A custom writer remains on v1 | Freeze a repository-wide inventory and add a search/contract gate before migration closeout. |
| Source rows consume memory | Insert rows incrementally or in internal bounded batches; do not expose tuning as result semantics. |
| A native scanner does not expose consumed bytes | Leave `bytes` and `sha256` null unless the adapter already has trustworthy observations. |
| Mid-read source mutation produces ambiguous identity | State the caller immutability contract; provenance describes resolved inputs, not a filesystem snapshot or physical read trace. |
| Rebuild blast radius is underestimated | Inventory maintained publications before implementation and stage replacements separately from package release. |
| Metadata and KEGG work become entangled | Merge and accept metadata v2 as its own change before the KEGG mapping implementation. |

## Rollback

Before package release, rollback is a code, fixture, and documentation revert.
No formal artifact is changed by repository implementation alone.

After a package release, do not reintroduce dual metadata silently. A rollback
requires a new package decision and coordinated publication rebuild because
metadata v1 and v2 are deliberately not dual-readable.

## Completion Criteria

This plan is complete when:

- `_bioextract.source_file` is the sole inventory in every maintained writer,
  validator, and inspection path;
- source records are supplied by resource adapters without shared-layer path
  probing or a required engine read stream;
- source byte counts and digests are nullable, and no public writer option
  triggers provenance-only hashing;
- metadata v1 and `bioextract.sources` are rejected without aliases or
  migration views;
- all publication fixtures and maintained resource paths use metadata v2;
- architecture, testing, rebuild, and compatibility documentation are current;
- `BIOEXTRACT_TEST_THREADS=1 pdm run check` passes; and
- package release and formal artifact replacement remain explicit, separately
  authorized follow-up actions.

## Execution Checkpoint

The 2026-08-13 v1.0 implementation checkpoint established the sole normalized
source inventory:

- shared and resource-specific writers and validators use metadata schema v2;
- `_bioextract.source_file` is the only source inventory and
  `bioextract.sources` is explicitly rejected;
- publication inspection and maintained hermetic fixtures use v2; and
- contract tests pass 400 cases and integration tests pass 267 cases with
  `BIOEXTRACT_TEST_THREADS=1`.

The coordinated v1.1 nullable-byte and no-hash-option correction was then
implemented across the shared layer and maintained resource validators. The
current `BIOEXTRACT_TEST_THREADS=1 pdm run check` gate passes with 792 tests,
format, Ruff, and Pyright. No formal publication, CephFS artifact, Git branch,
or package release is changed by this repository checkpoint; package release
and formal artifact replacement remain explicit follow-up actions.
