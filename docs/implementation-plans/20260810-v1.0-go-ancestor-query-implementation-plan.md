# GO Ancestor Projection And Publication Query Pushdown Implementation Plan

Version: v1.0
Date: 2026-08-10
Status: implemented
Authority: [Domain Access Architecture](../architecture/20260729-v1.0-domain-access-architecture.md), [GO And KEGG Tidy Architecture](../architecture/go-kegg-tidy.md), and [Repository Test Standard](../testing/README.md)

## Goal

Add one GO-owned domain selection that resolves caller-supplied GO term IDs to
canonical ontology ancestors and, optionally, projects those ancestors into an
OBO subset such as `goslim_generic`.

At the same time, move publication-backed GO domain reads from eager whole-table
loading to DuckDB query pushdown. `select_terms()`, `list_subsets()`, and the new
ancestor selection must execute their filtering, identifier resolution, joins,
and aggregation inside DuckDB and materialize only their final result frames.

The change preserves the existing nine-table GO publication, metadata-v1
provenance, ontology derivation, OBO parser, and source-backed behavior. It does
not require a publication rebuild or resource-schema migration.

## Settled Boundary

`bioextract` owns:

- validation and canonicalization of GO term IDs;
- alternate-ID resolution through `term_alternate_id`;
- traversal of the GO hierarchy represented by `term_ancestor`;
- the established `is_a + part_of` ancestor semantics;
- optional projection to a GO OBO subset through `subset_membership`;
- obsolete-term policy, self-distance semantics, deterministic output, and
  unmatched-input accounting; and
- equivalent result contracts for OBO-source and reopened-publication handles.

Downstream applications continue to own:

- protein, gene, protein-group, comparison-group, or cohort membership;
- splitting annotation cells into GO IDs and joining projected terms back to
  proteins or genes;
- Proteomics-specific output names or six-column schemas;
- ORA, GSEA, backgrounds, statistical filters, warning policies, stage
  metadata, and output paths; and
- cross-database or product-specific projections.

The first version does not add grouped GO selection. A caller can globally
deduplicate GO IDs, execute one ancestor selection, and join the result back to
its own membership relation. A future `select_groups()` requires evidence from
more than one caller that a generic `group_id` contract removes repeated
application logic.

## Public Query Contract

Add the following database method:

```python
selection = database.select_ancestors(
    ["GO:0008150", "GO:1234567"],
    target_subset_id="goslim_generic",
    include_self=True,
    resolve_alt_ids=True,
    include_obsolete=False,
)
```

Its settled signature is:

```python
def select_ancestors(
    self,
    term_ids: Iterable[str],
    *,
    target_subset_id: str | GoSubsetId | None = None,
    include_self: bool = False,
    resolve_alt_ids: bool = True,
    include_obsolete: bool = False,
) -> GOAncestorSelection:
    ...
```

`GOAncestorSelection` is a behaviorally public returned selection type. It is
defined in the GO implementation package, included in the repository behavior
and docstring tests, and not exported from the package root or the
`bioextract.go` resource package.

The selection exposes exactly two terminals:

```python
selection.extract_ancestors()
selection.extract_unmatched_ids()
```

Both return eager Polars `DataFrame` values. Their common resolution is cached
on the selection instance so calling both terminals does not repeat logical ID
resolution. The cache does not live on `GODatabase`, across selections, or at
process scope.

## Input And Resolution Semantics

Input handling preserves the current `select_terms()` behavior:

- strip surrounding whitespace;
- ignore empty strings;
- validate every retained value against the GO identifier grammar;
- raise `ValueError` for a malformed GO identifier rather than reporting it as
  absent from the snapshot;
- deduplicate repeated normalized IDs while retaining first-occurrence order;
  and
- resolve a primary GO ID directly before considering alternate-ID resolution.

When `resolve_alt_ids=True`, an input in `term_alternate_id.alt_go_id` resolves
to its `primary_go_id`. When false, that alternate ID is treated as absent
unless it independently exists as a primary term. Successful output always
retains both the caller's `input_go_id` and the resolved canonical `go_id`.

`include_obsolete=False` excludes both an obsolete resolved input term and an
obsolete ancestor term. If the input resolves only to an excluded obsolete
term, it is unmatched with `obsolete_excluded`. An obsolete target cannot
create an accepted ancestor match under the default policy.

## Ancestor And Subset Semantics

The existing `term_ancestor` relation remains authoritative for positive
distance traversal. It was derived from `is_a` and `part_of`; the query does
not reinterpret `term_relation` or introduce other OBO predicates.

When `include_self=True`, the query adds an explicit self candidate with
`min_distance=0`. The self candidate remains subject to the same obsolete and
target-subset policies as every positive-distance ancestor.

When `target_subset_id` is `None`, all policy-accepted ancestors are returned.
When it is set, only ancestors with the exact normalized
`subset_membership.subset_id` are returned. The parameter remains open text,
with `GoSubsetId` providing discoverable common values without closing the set
of valid subset IDs.

An unknown subset ID and a declared subset with no matching ancestors both
produce an empty match set and `no_matching_ancestor` for each otherwise valid
resolved input. This agrees with the existing `select_terms(subset_id=...)`
empty-result behavior and does not turn subset discovery into validation.

Multiple paths to the same ancestor produce one row with the existing
`term_ancestor.min_distance`. An input with at least one accepted ancestor row
does not appear in unmatched output.

## Result Schemas

`extract_ancestors()` returns:

| Column | Type | Meaning |
| --- | --- | --- |
| `input_go_id` | `String` | normalized caller-supplied GO ID |
| `go_id` | `String` | resolved canonical GO ID |
| `ancestor_go_id` | `String` | canonical ancestor or accepted self GO ID |
| `ancestor_term_name` | `String` | ancestor term name from `term` |
| `ancestor_namespace` | `String` | ancestor namespace from `term` |
| `min_distance` | `Int32` | shortest hierarchical distance; self is zero |
| `target_subset_id` | `String?` | requested target subset, or null when unfiltered |

Rows are unique and deterministic. They sort by retained input order,
`min_distance`, and `ancestor_go_id`. Input order is an execution field and is
not exposed in the final frame.

`extract_unmatched_ids()` returns:

| Column | Type | Meaning |
| --- | --- | --- |
| `input_go_id` | `String` | normalized caller-supplied GO ID |
| `resolved_go_id` | `String?` | canonical ID when resolution succeeded |
| `reason` | `Enum` | why no accepted ancestor row exists |

Reason values and precedence are:

1. `not_found` — no primary or allowed alternate-ID target exists;
2. `obsolete_excluded` — the resolved input exists but is excluded by policy;
3. `no_matching_ancestor` — the accepted input has no ancestor satisfying the
   self and subset policies.

Empty selections return frames with these exact schemas.

## Publication Query Boundary

`GODatabase._read_publication_frames()` remains the explicit complete-frame
loader for `from_duckdb(...).build_tidy()`. A caller requesting the complete
tidy dataset is intentionally requesting every published biological frame.

Publication-backed domain methods must not use that loader. They open a fresh
validated read-only connection, execute a resource-specific DuckDB query, and
convert only the final query result to Polars:

```text
from_duckdb(...).build_tidy()
    -> _read_publication_frames()
    -> complete nine-table materialization

select_terms()
list_subsets()
select_ancestors()
    -> DuckDB domain SQL
    -> predicate and join pushdown
    -> final result DataFrame only
```

The implementation does not add a generic SQL, query, filter, or DataFrame
facade. Query text and schema handling remain local to the GO resource.

## Parameterized Input Relation

Publication queries pass normalized unique GO IDs as one DuckDB list parameter
and derive their input relation with ordinality:

```sql
WITH input AS (
    SELECT
        input_go_id,
        input_order - 1 AS input_order
    FROM unnest(?) WITH ORDINALITY
         AS input(input_go_id, input_order)
)
```

This avoids a temporary input table, a registered Polars relation, and a
dynamically expanded `IN (?, ?, ...)` statement. It preserves input order and
keeps the identifier set inside one set-oriented DuckDB plan.

The currently installed Polars does not provide `scan_database()`. Database
batch iteration would bound transfer chunks but would not push GO predicates
or joins into DuckDB. The implementation therefore uses explicit DuckDB SQL
rather than presenting an eager database read as a lazy Polars scan.

Do not add an input-size threshold that switches between `UNNEST` and a
temporary table without a reproducible benchmark demonstrating a material
problem at representative GO ID volumes.

## Source-Backed Execution

An OBO-source handle continues to use the existing cached tidy frames. The
source path may implement the selection with Polars joins over `term`,
`alt_id`, `ancestor_all`, and `subset_membership`; it does not need to imitate
the physical DuckDB plan.

Source execution already materializes the derived ancestor frame as part of
the current tidy construction model. This plan's prohibition on whole-table
publication reads does not redesign source graph derivation or pretend that a
source-backed Polars frame is a database scan.

Source and publication execution must nevertheless return equal schemas,
values, unmatched reasons, and ordering for the same snapshot and parameters.
Shared normalization, output-schema, reason, and sorting definitions should
remain local to the GO query module so the two execution strategies do not
silently diverge.

## Delivery Slices

### Slice 1: Freeze the query contract

Predecessor: this plan.

Add contract and integration tests for the new signature, result schemas,
normalization, alternate IDs, obsolete policy, subset behavior, self distance,
reason precedence, and deterministic ordering. The tests may initially fail
because the implementation is absent, but they must not change existing GO
publication fixtures or table contracts.

Slice-local non-goals are implementation optimization, grouped selection, and
real-snapshot publication work.

Acceptance: the tests fully describe the externally observable selection
behavior without requiring an implementer to infer a missing policy.

### Slice 2: Push existing publication domain reads into DuckDB

Predecessor: Slice 1's compatibility expectations for existing methods.

Implement publication SQL paths for `select_terms()` and `list_subsets()`.
Preserve their current columns, types, ordering, alternate-ID behavior,
obsolete defaults, subset behavior, exceptions, and pinned-publication identity
checks. Keep `_read_publication_frames()` for explicit full tidy reads.

Add a regression test that fails if these publication domain methods call the
complete-frame loader. Compare each optimized publication result with the
existing source-backed result.

Slice-local non-goals are ancestor selection and generic publication-query
abstractions.

Acceptance: existing source/publication parity passes and publication domain
reads materialize only final results.

### Slice 3: Implement ancestor selection

Predecessors: Slice 1 contract and Slice 2 publication query boundary.

Add `GOAncestorSelection`, parameterized `UNNEST` publication execution,
source-backed Polars execution, self-candidate handling, subset projection,
ancestor annotation, unmatched reasons, and selection-local caching.

Add a regression test proving that publication-backed ancestor extraction does
not use `_read_publication_frames()`. Calling the second terminal on the same
selection must reuse the first resolution; creating a new selection must
perform an independent resolution.

Slice-local non-goals are grouped fan-out, temporary-table heuristics, GAF or
GPAD inputs, and direct output writers.

Acceptance: matched and unmatched results are equal between source and reopened
publication handles for every compact-fixture policy case.

### Slice 4: Documentation and final convergence

Predecessor: accepted Slice 3 behavior.

Update the GO architecture, resource test standard, README example, and any
behavior matrix descriptions to state the implemented contract. Remove only
the obsolete non-goal that says arbitrary GO IDs cannot be projected to slim
ancestors; retain the GAF/GPAD, protein/gene mapping, and enrichment non-goals.

Acceptance: documentation describes the delivered API, unchanged publication
schema, execution boundary, and downstream ownership without presenting the
internal selection class as a stable package export.

## Compatibility And Publication Decision

The change is additive before v1.0. Existing imports, constructors,
`select_terms()`, `list_subsets()`, `build_tidy()`, `connect()`, and
`write_duckdb()` remain available with unchanged caller-visible behavior.

`GOAncestorSelection` receives no top-level or resource-package export. No
compatibility alias, generic selection base class, sidecar, filename-derived
identity, or grouped-selection facade is added.

The main-schema tables, physical columns, table roles, row counts,
`resource_schema_version`, source schema profile, and `_bioextract` relations
remain unchanged. Existing GO DuckDB publications can serve the new query
without rebuilding. Query behavior is a Python API addition, not a publication
schema migration.

## Risks And Mitigations

- **Source and publication drift:** separate Polars and SQL execution can
  disagree on nulls, ordering, or types. Use explicit result schemas and direct
  frame equality across every policy case.
- **Existing-query compatibility regression:** moving `select_terms()` and
  `list_subsets()` into SQL can change order or empty-frame dtypes. Freeze their
  current outputs before the optimization and retain parity tests.
- **Accidental whole-table materialization:** a helper reuse could route domain
  queries through `_read_publication_frames()`. Add a test that makes such a
  call fail.
- **Unbounded interface growth:** grouped selection, arbitrary query wrapping,
  protein mapping, and direct writers can expand the feature beyond ontology
  projection. Keep them outside this plan.
- **Large parameter-list behavior:** `UNNEST` may eventually need measurement
  at unusually large input volumes. Do not add an unmeasured threshold; record
  a reproducible benchmark before changing strategies.
- **Obsolete semantics ambiguity:** applying the flag only to inputs or only to
  targets would be surprising. Test the settled rule that it governs both.

## Rollback And Cleanup

Before a package release, rollback consists of removing the additive
`select_ancestors()` method and internal selection implementation, then
restoring the prior publication-backed implementations of `select_terms()` and
`list_subsets()` if their pushdown paths cannot preserve compatibility.

No publication rollback, resource deletion, CephFS cleanup, metadata migration,
or schema downgrade is required. Existing DuckDB publications remain valid
through implementation and rollback.
