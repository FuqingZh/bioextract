## Goal

Make large bioextract domain queries lazy, composable, and safe to execute with
native Polars without changing the repository into a generic query engine. The
delivery covers five immediate resource needs:

1. replace eager public relation terminals with native `polars.LazyFrame`
   relations and noun-based names;
2. expose a non-Cartesian Rhea-to-UniProt neighborhood as
   `List(Struct)` while retaining normalized edge relations;
3. add species-scoped WikiPathways access that behaves identically for source
   handles and reopened publications and cannot leak Entrez Gene IDs across
   species;
4. add a public, provenance-preserving InterPro Pfam relation so downstream
   Proteomics never reads private modules or DuckDB implementation tables;
5. benchmark the existing lazy UniProt idmapping scan before considering any
   publication-backed selected-ID API.

This is a public-contract and storage-execution convergence plan. It is not a
request to publish a package, rebuild formal snapshots, or change downstream
Proteomics in the same repository change.

## Decision Summary

| Concern | Decision |
| --- | --- |
| Public tabular result | A domain relation method returns a native `pl.LazyFrame`. |
| Execution | Callers use Polars `collect()`, `collect_batches()`, and `sink_*()` directly. bioextract does not wrap them. |
| Lifetime | A returned lazy frame owns a frozen, replayable query description; it does not retain an open DuckDB connection or borrow the selection object. |
| Context manager | No `with` block is required to obtain or execute a lazy relation. `connect()` remains the separate caller-owned SQL escape hatch. |
| Naming | Derived domain relations use nouns such as `reactions()` and `mappings()`. `scan_*` is reserved for a physical source scan. |
| Result limits | No public `max_rows`, `batch_size`, or equivalent truncation parameter is added. `.limit()` is explicit query semantics; batch sizing stays an internal execution hint. |
| One-to-many output | Keep normalized edge relations and add a reaction-centric nested Rhea relation with `List(Struct)` fields. Never construct the default `input_id × reaction × UniProt` flat product. |
| External Rhea xrefs | `cross_references()` contains external reaction xrefs only. UniProt mappings have their own relation; no implicit public `UNION ALL`. |
| WikiPathways species | `with_species()` applies the same exact normalized species scope to pathway metadata and to pathway-gene membership through a pathway semi-join. |
| Pfam | Public `pfam_annotations()` works from eligible source handles and reopened publications and includes caller lineage plus exact InterPro trace. |
| UniProt idmapping | Keep and benchmark `scan_mapping(taxon_ids=...)`. Add no selected-ID API unless a recorded caller workload still misses an explicit operational budget. |
| Compatibility | This is an intentional pre-v1 Python API break. Do not retain `extract_*` aliases or add `lazy=` compatibility flags. Existing compatible DuckDB publications remain readable. |

## Motivation And Evidence

A full Rhea/UniProt run was observed still computing after about 12 minutes
with resident memory near 212 GB, approximately 40% of the host. This was not a
functional failure. It is evidence that the current backend can over-materialize
large relations, especially when it expands every selected input through every
reaction to every associated UniProt entry.

One inspected workload had the following cardinalities:

| Relation or projection | Cardinality |
| --- | ---: |
| input-to-reaction edges | 2,844 |
| distinct selected reactions | 1,017 |
| selected reaction-to-UniProt edges | 14,386,772 |
| implied per-input flat child elements | 475,508,198 |

These values explain the shape of the failure but are not yet a formal
benchmark baseline. The implementation must record snapshot identities,
request identity, versions, elapsed time, and peak RSS before using them as a
release comparison.

Public row caps do not solve this problem. They silently change biological
result semantics, make completeness depend on execution tuning, and do not
remove the oversized intermediate relation. The correct optimization is to
preserve normalized cardinality, nest deliberate one-to-many values, stream
ordered edges, and let the caller choose when and how to materialize.

## Assumptions

- `polars`, DuckDB, and PyArrow remain core runtime dependencies.
- Database handles pin caller-supplied source or publication identities at
  construction, as documented by the current resource contracts.
- Selection inputs are small enough to retain as normalized immutable values;
  biological expansion is not retained eagerly.
- Existing publication tables are authoritative. A public relation may reshape
  their rows but must not infer biological relationships that are absent from
  the owning source.
- Public row order is not part of relation semantics unless a resource contract
  explicitly says otherwise. Callers that need row order use `.sort(...)`.

## Unified Public Relation Contract

### Return and ownership semantics

Every behaviorally public method whose purpose is to expose a tabular biological
relation returns `pl.LazyFrame`. Calling the method constructs a query plan; it
does not execute source parsing, issue SQL, fetch rows, or open a long-lived
connection.

```python
selection = database.select_ids(ids, namespace="chebi")
lf = selection.reactions()

# The selection and database variables do not own an open query cursor.
del selection

df = lf.collect()
lf.sink_parquet("selected-reactions.parquet")
```

The lazy frame captures immutable values needed to replay the operation:

- exact source or publication identity;
- declared capability and frozen output schema;
- normalized selection and group membership;
- parameterized domain query description;
- resource-specific transformation policy.

This is snapshot-by-value ownership, not a move-only API. The selection remains
usable, multiple lazy relations may be created from it, and the same lazy frame
may be collected more than once. Each execution opens fresh resources and
closes them on completion, cancellation, iterator abandonment, or error.

### Error timing

Errors that require no I/O remain immediate:

- invalid or empty normalized parameters;
- unsupported namespace;
- a capability known to be absent from the validated handle.

Execution errors are deferred to `collect()`, `collect_batches()`, or `sink_*()`:

- a source or publication was replaced after handle construction;
- a file became unavailable;
- DuckDB or parser execution failed;
- emitted rows violate the frozen schema.

`collect_schema()` must return the frozen schema without executing the
biological query or parsing the source.

### Native Polars execution

bioextract does not implement these methods:

```python
df = lf.collect()

for df_batch in lf.collect_batches():
    consume(df_batch)

lf.sink_parquet("result.parquet")
lf.sink_csv("result.csv")
lf.sink_ipc("result.arrow")
lf.sink_ndjson("result.ndjson")
```

The exact execution methods available are those supported by the declared
Polars dependency. bioextract owns only the lazy data source and domain
relation. It must not add `collect_*` or `sink_*` forwarding methods to database
or selection classes.

`lf.limit(n)` remains available because it is visible query semantics. It is
not treated as a safety guarantee or an implicit default.

### Naming rules

- Use a plural relation noun when rows represent multiple entities or edges:
  `reactions()`, `participants()`, `mappings()`, `unmatched_ids()`.
- Use `scan_<physical_source>()` only when the method exposes a physical scan,
  such as `scan_mapping()` for UniProt idmapping.
- Keep lifecycle verbs for lifecycle operations: `select_ids()`,
  `select_groups()`, `with_species()`, `write_duckdb()`, and `connect()`.
- Do not use `extract_*` for a lazy relation and do not add a `lazy` flag to
  change a return type.

## Shared Lazy Execution Adapter

### Internal boundary

Add one internal adapter, provisionally `bioextract._lazy`, that converts a
frozen source/query description into a native `pl.LazyFrame`. Resource modules
own biological SQL and parsing; the adapter owns lifecycle, schema, and batch
delivery only.

For DuckDB-backed relations, one execution performs the following sequence:

1. verify the pinned publication identity;
2. open a fresh read-only DuckDB connection;
3. create selection input relations with bound parameters or Arrow input;
4. execute the resource-owned parameterized query;
5. expose Arrow record batches to Polars;
6. close the reader and connection in `finally` for success, failure, or early
   termination.

The lazy frame must not capture a `DuckDBPyConnection`, cursor, or DuckDB
relation. Implementations based on `fetchall()`, eager
`pl.read_database(...).lazy()`, or a DuckDB lazy relation whose connection is
left open are prohibited.

For native file formats, prefer Polars `scan_*` sources. For parser-backed
formats such as GMT or XML, execution uses a replayable internal source callback
with the same identity and cleanup rules.

### Polars compatibility spike

The first implementation slice verifies the declared Polars version range
against its custom I/O source surface, initially
`pl.io.plugins.register_io_source`, and Arrow batch behavior. Because that API
is marked unstable by Polars, bioextract must:

- isolate it in one private module;
- expose no Polars plugin types through the public API;
- test the minimum and locked dependency versions;
- fail the compatibility spike before resource migration if projection, slice,
  schema, repeated collection, or cleanup behavior is incorrect;
- adjust the supported Polars version range from evidence rather than add a
  second public execution abstraction.

Projection and slice pushdown may be enabled only when the adapter implements
them correctly. Predicate pushdown remains disabled until a tested expression
translation exists; Polars may apply predicates to streamed batches instead.
The adapter must never claim a pushdown and silently omit a filter.

### Internal batching

Arrow batch size is an execution hint and never changes which rows are emitted.
It is private, adaptive where useful, and tested through memory/lifecycle
behavior rather than exposed as a caller contract. No batch is allowed to
truncate a logical row or a nested list.

## Rhea Relations And `List(Struct)`

### Normalized relations

A reaction selection exposes two independent normalized edges:

```text
matches:
    [group_id,] input_id, input_namespace,
    rhea_id, master_id, direction

uniprot_mappings:
    rhea_id, master_id, direction,
    uniprot_id, uniprot_section
```

`uniprot_mappings()` is restricted to distinct reactions matched by the
selection, but it does not repeat a UniProt edge for every input that found the
same reaction. Callers that want relational normalization can join it to
`matches()` explicitly.

`cross_references()` reads only `reaction_xref` and returns:

```text
[group_id,] input_id, input_namespace,
rhea_id, master_id, direction,
reference_database, reference_id
```

It no longer unions `reaction_uniprot` into the relation and therefore no longer
contains `uniprot_section`.

### Nested neighborhood relation

`uniprot_neighborhoods()` is the ergonomic one-to-many view. It returns one row
per distinct selected reaction:

```text
rhea_id: Int64
master_id: Int64
direction: String
inputs: List(
    Struct({
        group_id: String,       # grouped selections only
        input_id: String,
        input_namespace: String,
    })
)
uniprot_entries: List(
    Struct({
        uniprot_id: String,
        uniprot_section: String,
    })
)
```

Invariants:

- reaction rows are unique by `(rhea_id, master_id, direction)`;
- `inputs` is non-empty and contains unique lineage structs;
- `uniprot_entries` is an empty list, not null, when a matched reaction has no
  UniProt mapping;
- UniProt entries are unique by the complete source pair
  `(uniprot_id, uniprot_section)`;
- both lists use deterministic lexical ordering of their struct fields;
- no internal or public step constructs the cross product of the two lists.

### Caller usage

Keep one row per reaction and choose native Polars execution:

```python
lf = selection.uniprot_neighborhoods()
lf.sink_parquet("rhea-uniprot-neighborhoods.parquet")
```

Obtain one row per input-reaction while retaining the UniProt list:

```python
by_input_reaction = (
    selection.uniprot_neighborhoods()
    .explode("inputs")
    .unnest("inputs")
)
```

Flatten UniProt entries only when the caller explicitly needs the expanded
relation:

```python
flat = (
    selection.uniprot_neighborhoods()
    .explode("inputs")
    .unnest("inputs")
    .explode("uniprot_entries")
    .unnest("uniprot_entries")
)
```

The last form may be intrinsically large. Its materialization is a visible
caller decision rather than an implicit bioextract default.

### Streaming assembly

The nested backend reads the input-to-reaction and reaction-to-UniProt edges in
reaction order and performs a streaming merge/group. It retains only the
current reaction's members plus bounded output batches. It must not implement
the relation with a global flat join followed by `group_by(...).agg(list())`.

The intended memory complexity is proportional to the largest single reaction
neighborhood, normalized selection state, and in-flight Arrow batches, not to
the flattened `input × reaction × UniProt` cardinality. DuckDB may use its own
bounded execution buffers or spill mechanics, but no such setting changes
result completeness and no public tuning parameter is added.

## WikiPathways Species Scope

### API

Add the Reactome-aligned resource view:

```python
db = WikiPathwaysDatabase.from_gmt("wikipathways-*.gmt")
human = db.with_species("Homo sapiens")

pathways_lf = human.pathways()
mapping_lf = human.select_ids(["7157"]).mappings()
```

The same operation must work after publication reopen:

```python
db = WikiPathwaysDatabase.from_duckdb("wikipathways.duckdb")
mapping_lf = (
    db.with_species("Homo sapiens")
    .select_ids(["7157"])
    .mappings()
)
```

`with_species(species: str) -> WikiPathwaysDatabase` trims whitespace, rejects
an empty result, performs exact case-sensitive matching, and returns a new
lightweight handle sharing the pinned snapshot/publication identity. Reapplying
it replaces the previous species scope. The current scope is inspectable as
`database.species`.

Remove `species=` from `from_gmt()` in the same pre-v1 migration so source
construction and query scope have one unambiguous API.

### Correctness rule

The species filter is defined by pathway identity, not by the presence of a
`species` column on every table:

```text
scoped_pathway = pathway WHERE pathway.species == requested_species

scoped_pathway_gene = term2gene
    SEMI JOIN scoped_pathway USING (wiki_pathways_id)
```

Every scoped relation follows that root:

- `pathways()` filters `pathway` directly;
- `pathway_genes()` keeps only genes whose pathway is in `scoped_pathway`;
- `pathway_names()` derives from `scoped_pathway`;
- selection `mappings()` joins input IDs only to `scoped_pathway_gene`, then to
  `scoped_pathway`;
- `unmatched_ids()` is computed after that scoped mapping, independently per
  group for grouped selections.

Filtering only `pathway` after an unscoped input-to-gene join is not sufficient.
An Entrez Gene ID can occur in more than one species; the implementation must
never use that shared identifier to carry a pathway mapping from one species
into another.

### Publication scope metadata

The physical `pathway`, `term2gene`, and `term2name` schemas remain
unchanged. New publications written from a scoped handle record the normalized
species in the existing `bioextract.scope` metadata as canonical JSON. Reopened
handles read that metadata:

- an unscoped or older publication can be narrowed with `with_species()`;
- a publication declaring the same species can be reopened and narrowed
  idempotently;
- a publication declaring a different single-species scope raises
  `CapabilityError` rather than pretending the missing species is available.

Older compatible publications without scope metadata remain readable. They are
treated as having no declared scope; query correctness is still enforced by
the rows present in the publication. Formal scoped publications created before
this metadata rule should be rebuilt during an explicitly authorized release
operation so their completeness can be audited.

## InterPro Pfam Public Relation

### API and capability

Expose `pfam_annotations()` on `InterProDatabase` and `InterProSelection`:

```python
db = InterProDatabase.from_mapping_files(
    protein_to_interpro="protein2ipr.dat.gz",
    interpro_xml="interpro.xml.gz",
)

pfam_lf = db.select_ids(["P04637"]).pfam_annotations()
```

The full database relation returns
`uniprot_id, pfam_id, pfam_name, interpro_id, interpro_name, interpro_type`
without caller lineage. A selection prefixes lineage and returns this exact
column order:

```text
group_id             # grouped selections only
input_id
input_namespace
uniprot_id
pfam_id
pfam_name
interpro_id
interpro_name
interpro_type
```

This is an annotation-level relation. Repeated positional occurrences of the
same `(uniprot_id, pfam_id, interpro_id)` are deduplicated. Callers that need
domain occurrence coordinates use the public `mappings()` relation and filter
`member_db == "PFAM"`; `pfam_annotations()` does not silently discard that
lower-level API.

The operation requires the mapping capability and InterPro XML-derived Pfam
metadata. A source handle lacking XML or a mapping-only publication raises a
targeted `CapabilityError` based on known capability metadata. Source and
reopened-publication results must have identical schema and values.
Release-level trace stays on the database/publication metadata instead of
being repeated on every annotation row; the row fields preserve the exact
protein-to-Pfam-to-InterPro lineage within that pinned release.

### Trace correctness

The public relation is derived from exact mapping rows whose `member_db` is
Pfam and whose member identifier is a valid Pfam ID. It must not recover
InterPro lineage by joining `protein_term` to `term_xref` on `pfam_id` alone:
one Pfam identifier can have more than one InterPro association, and that join
can invent protein-to-InterPro pairs.

The safe derivation is:

1. filter the canonical mapping to exact Pfam member rows;
2. preserve the row's protein, Pfam, and InterPro association;
3. deduplicate positional repeats at annotation granularity;
4. join the Pfam term relation only to obtain `pfam_name`;
5. prepend normalized input and optional group lineage for a selection.

Proteomics consumes only this public API. It must not import
`bioextract.interpro._pfam`, call private helpers, or query `protein_term`,
`term`, or `term_xref` directly through DuckDB.

## UniProt Idmapping Decision Gate

`UniProtDatabase.scan_mapping(taxon_ids=...)` already expresses the correct
physical lazy scan contract and remains named `scan_mapping`. Remove the eager
`read_mapping()` convenience; materialization is explicit:

```python
mapping_lf = database.scan_mapping(taxon_ids=[9606])
human = mapping_lf.collect()
```

Before adding any selected-ID API, benchmark the existing path for the actual
downstream workload across the applicable source representations:

- raw plain or gzip `idmapping_selected`;
- Parquet or Hive-partitioned mapping data;
- reopened DuckDB publication;
- cold and warm executions;
- taxon-only and taxon-plus-selected-ID Polars plans.

Record source/publication identity, dependency versions, normalized taxon and
ID request hash, row count, stable content checksum, wall/CPU time, peak RSS,
and execution mode. Verify that the shared adapter also fixes the current
publication scan's connection lifetime; a returned lazy frame may not rely on
the connection created inside `_scan_mapping()` remaining open.

No publication-backed selected-ID API is added merely because point lookup is
theoretically faster. It requires both:

1. an explicit downstream workload and accepted operational time/memory budget
   that the optimized `scan_mapping(taxon_ids=...)` plan still misses; and
2. a benchmark showing that a publication-backed indexed selection materially
   meets that budget without changing rows or provenance.

If either condition is absent, the decision is “no new API.” If both are met,
the selected-ID contract is designed and reviewed as a separate additive
slice. It should extend the established selection vocabulary and expose lazy
`mappings()` and `unmatched_ids()` relations; its exact namespace and index
contract is not frozen by this plan before evidence exists.

## Compatibility And Migration

### Python API

The target package is a pre-v1 breaking release. Update bioextract callers in
one coordinated migration:

```python
# before
df = selection.extract_reactions()

# after
lf = selection.reactions()
df = lf.collect()
```

Do not keep old methods as aliases, return different types based on a flag, or
materialize automatically when a downstream caller expects a `DataFrame`.
These approaches preserve ambiguity and make large-query safety dependent on
call history.

### Publication compatibility

- Rhea tables and views remain unchanged; compatible publications reopen
  without rebuild.
- InterPro mapping and Pfam publication tables remain unchanged; the new public
  relation is derived from existing capabilities.
- UniProt idmapping tables remain unchanged.
- WikiPathways biological table schemas remain unchanged; new scoped writes add
  optional metadata using the existing metadata contract.
- Publication identity is rechecked at every lazy execution.
- No filename-derived schema or compatibility sidecar is introduced.

### Downstream Proteomics

The downstream migration is a separate change after a compatible bioextract
package is available. It must:

- depend on the public package version that contains `pfam_annotations()`;
- use returned lazy relations and native Polars composition;
- choose `.collect()` or `sink_*()` at its own execution boundary;
- remove imports of private InterPro modules and SQL against bioextract
  implementation tables;
- validate output equivalence on a pinned representative request.

## Performance Acceptance

The plan deliberately does not define success as “return at most N rows” or
“use batches of N rows.” Acceptance is structural and measured:

1. no implicit flat input/reaction/protein relation exists in the public or
   internal plan;
2. nested construction uses ordered normalized streams and bounded in-flight
   batches;
3. memory growth on scale-doubling fixtures follows the largest logical group
   and batch working set rather than flat-product cardinality;
4. the pinned real Rhea sink reaches a stable memory plateau and completes or
   reports an external operational limit without risking host OOM;
5. result edge counts and checksums reconcile with normalized source relations;
6. UniProt API expansion is decided against an explicit caller budget, not a
   synthetic row cap.

The initial 212 GB observation is retained as motivating evidence. It becomes a
comparison baseline only if the same snapshot, request, dependency versions,
and measurement method can be reproduced safely.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| Polars custom I/O API changes | One private adapter, minimum/locked-version tests, evidence-driven dependency range, no public wrapper. |
| Lazy frame outlives source validity | Pin identity in the frozen plan and revalidate on every execution. |
| Connection leak on partial consumption | Generator/reader `finally` cleanup and explicit abandoned-iterator tests. |
| One reaction itself has an unusually large list | Stream all other groups and measure the largest-group bound; do not split or truncate one biological row. |
| Nested output hides expensive caller expansion | Document `explode` explicitly and keep flattening a visible caller operation. |
| Cross-species Entrez collision | Derive pathway-gene scope by semi-joining to scoped pathways before input matching. |
| Pfam-only joins invent trace | Derive protein/Pfam/InterPro triples from exact mapping rows and test multi-mapping collisions. |
| Breaking downstream eager assumptions | One pre-v1 coordinated rename, explicit `.collect()` migration, public-only Proteomics validation. |
| Benchmark noise produces a false API need | Pin identities, run cold/warm repeats, reconcile content, and require an explicit caller budget. |
| Older Wiki publication has undeclared partial scope | Keep it readable, treat scope as undeclared, and require an authorized rebuild before completeness claims. |

## Rollback

Before package release, rollback is a normal code and documentation revert. No
publication rollback is required because biological table schemas are not
rewritten by this work and formal artifacts are outside the implementation
scope.

After a package release, do not silently restore eager aliases. A correction to
public return types or names requires another versioned pre-v1 release and a
documented downstream migration. If the Polars source adapter proves unsafe,
preserve the normalized and species/Pfam correctness work on an unreleased
branch, revert the adapter and public migration together, and keep the recorded
benchmark evidence for the next design review.
