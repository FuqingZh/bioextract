# KEGG Mapping Aggregate Publication Implementation Plan

Version: v1.2
Date: 2026-08-14
Status: P3 DuckDB-native publisher accepted on the fixed 1,000-organism scope;
P4 canonical CI gate passed; implementation plan complete; release held
separately
Target: pre-v1 KEGG mapping contract candidate; release separately authorized
Prerequisite:
[Publication Metadata v2 Source Inventory Migration Plan](20260813-v1.0-publication-metadata-v2-migration-plan.md)

### 2026-08-14 amendment

The biological API, three-table publication schema, organism scope, and
`List(Struct)` semantics in this plan remain accepted. The
[performance optimization plan](20260813-v1.0-kegg-mapping-performance-optimization-plan.md)
v1.2 supersedes the earlier physical-reader requirements that provenance be
captured through the same content stream, that every file be opened exactly
once, that every fatal error contain a line number, or that exact duplicates
emit per-file warnings.

The accepted publisher uses a resolved logical input inventory, native
DuckDB multi-file role scans, set-oriented validation, and organism/key-bounded
nested aggregation. Source membership is durable provenance; physical read
count and scheduling are engine observations. Source byte counts and digests
are nullable, and the public `include_source_hashes` option is removed by the
coordinated metadata amendment. Exact duplicate relationships are normalized
silently, while conflicting metadata and invalid biological identifiers remain
fatal. Eight private hash windows cap execution state; this is not a public row
limit or tuning parameter.

## Goal

Replace the current one-organism, wide Cartesian KEGG `mapping` relation with
a lazy multi-organism domain API and one compact DuckDB publication containing
aggregated `List(Struct)` relationships.

The implementation must:

1. read one explicit organism directory or a caller-supplied directory
   containing any available subset of KEGG organisms;
2. avoid recursively materializing every organism and every many-to-many
   combination in memory;
3. expose source and reopened-publication relations as native replayable Polars
   `LazyFrame` plans;
4. preserve direct gene-pathway observations separately from pathways derived
   through KO membership;
5. publish a fixed three-table serving schema with explicit capabilities,
   provenance, and organism scope; and
6. remain independent of biofetch, `manifest.lock`, downstream applications,
   and organization-specific resource roots.

## Decision Checkpoint

The architecture choices in this plan are accepted. Implementation may revise
an internal mechanism when executable evidence disproves it, but it must not
silently change these public and publication contracts.

| Concern | Accepted decision |
| --- | --- |
| Multi-organism input | `from_mapping_directory(source, *, ...)` reads the organisms actually available under one direct root. It does not assert that the root is a complete KEGG release. |
| One-organism input | `from_mapping_files(source=None, *, organism_code, ...)` accepts a direct organism directory, explicit role files, or both. |
| `source` meaning | In every factory, `source` is the direct discovery root owned by that factory, never the parent of that root. |
| Source overlays | Explicit non-`None` paths replace the matching convention; `source` fills omitted roles. No parent-directory climb occurs. |
| Lazy ownership | Relation methods return a transferred, replayable `pl.LazyFrame` plan. No `with` block is required. |
| Execution terminals | Callers use native Polars `collect()`, `collect_batches()`, and `sink_*()`. bioextract does not wrap them. |
| Result size | No public `max_rows`, `batch_size`, pagination, or truncation contract. Internal batching never changes biological completeness. |
| Organism scope | `with_organisms()` is the explicit physical-pruning and publication-scope API. |
| Storage shape | DuckDB stores aggregated serving rows only: `organism`, `gene_annotation`, and `ko_annotation`. |
| One-to-many values | Biological mappings are nullable `List(Struct)` fields; gene aliases remain `List(String)` attributes. |
| Edge access | Mechanical flattening uses Polars `explode()` and `unnest()`. bioextract adds only the domain-owned `gene_pathways_via_ko()` traversal. |
| Relationship truth | Direct gene-pathway rows are never implicitly unioned with gene-to-KO-to-pathway derivations. |
| Metadata | Shared metadata v2 is a prerequisite; `_bioextract.source_file` is the sole source inventory. |
| Compatibility | Remove old `mappings()` and the physical `mapping` table. Add no aliases, flags, or automatic publication migration. |
| Delivery | Metadata v2 and KEGG mapping are separate review changes. One package release may follow both; formal artifact replacement is separately authorized. |

## Motivation And Bounded Source Evidence

A bounded inspection of the caller-identified
`/cephfs_data/genostack_v3/genostack_php/public_file_data/database/bioinfo/resources/kegg/mapping/2026-06/raw`
subtree observed:

| Observation | Value |
| --- | ---: |
| Organism directories | 11,782 |
| Files | 58,912 |
| Raw bytes | about 7.81 GiB |
| Organism files per complete directory | 5 |
| Global files | `organism/list_organism.tsv` and `ko/ko_pathway.tsv` |
| Top-level directory enumeration | about 1.604 s in the observed run |
| Full two-pass file `stat()` walk | exceeded the bounded 60 s observation |

Zero-byte organism files occur and represent an observed empty relation, not a
missing capability. The actual `gene_list.tsv` profile contains four columns;
the current two-column reader can therefore interpret the gene type, such as
`CDS`, as a symbol. The global KO-pathway file contains both `path:map.....` and
`path:ko.....` namespaces.

These measurements motivate the design but are not universal KEGG constants.
The implementation must record a reproducible real-snapshot benchmark before
making performance claims. Tests and development commands must not recursively
scan `/cephfs_data` or write to the formal resource tree.

The current wide relation joins UniProt, NCBI Gene, KO, and pathway edges at
gene grain. Each independent one-to-many branch multiplies the others, so both
source access and publication size can grow far beyond the normalized facts.
Public row limits would hide incomplete biology without fixing that
intermediate shape. Aggregating each relation into one nested field per gene
removes the cross-product while retaining every observed edge.

## Scope

### In scope

- directory and file-overlay constructors for local KEGG mapping snapshots;
- one or many organism mappings, including caller-supplied partial collections;
- optional global organism and KO-pathway files;
- explicit organism-scoped handles and scoped publication;
- fixed aggregate source and DuckDB schemas;
- direct and KO-derived pathway relations;
- UniProt, NCBI Gene, and KEGG gene selections;
- grouped selections without input-to-annotation cross-products;
- native replayable `LazyFrame` execution;
- a KEGG-specific staged multi-table DuckDB publisher;
- metadata-v2 capabilities, source inventory, scope, and validation;
- parser, contract, integration, real-snapshot benchmark, and migration
  documentation.

### Out of scope

- downloading, API calls, mirroring, retry, or release scheduling;
- any dependency on biofetch or its `manifest.lock`;
- claiming that a caller directory is the complete KEGG organism catalog;
- whole-directory snapshot isolation or source mutation detection;
- NCBI taxonomy inference or online organism enrichment;
- enrichment statistics or downstream analysis policy;
- a generic SQL/query facade or wrappers around Polars execution terminals;
- generic KO or pathway identifier selection in `select_ids()`;
- public concurrency, memory budgets, row limits, or transaction tuning;
- ART indexes or a duplicate normalized edge layer in the initial publication;
- automatic migration of the old wide `mapping` publication;
- package release, formal CephFS replacement, or old-artifact deletion.

## Public Construction Contract

### Factories

The mapping factories become:

```python
KEGGDatabase.from_mapping_directory(
    source,
    *,
    organism_list=None,
    ko_pathway=None,
    release_version=None,
)

KEGGDatabase.from_mapping_files(
    source=None,
    *,
    organism_code,
    gene_list=None,
    uniprot_conversion=None,
    ncbi_gene_conversion=None,
    gene_ko=None,
    gene_pathway=None,
    organism_list=None,
    ko_pathway=None,
    release_version=None,
)
```

`source` is the first positional-or-keyword parameter and all other parameters
are keyword-only.

The two factories intentionally give `source` different concrete directory
depths while preserving one architectural meaning: it is always the direct
discovery root for that factory.

| Factory | Meaning of `source` | Conventional children |
| --- | --- | --- |
| `from_mapping_directory` | Root containing many organism directories plus optional reserved global directories. | `source/hsa/...`, `source/mmu/...`, `source/organism/list_organism.tsv`, `source/ko/ko_pathway.tsv` |
| `from_mapping_files` | Directory for exactly the declared `organism_code`. | `source/gene_list.tsv`, `source/conv_uniprot.tsv`, `source/conv_ncbi_geneid.tsv`, `source/gene_ko.tsv`, `source/gene_pathway.tsv` |

The file factory never climbs from an organism directory to its parent to find
`organism/` or `ko/`. Global roles are available there only when passed
explicitly. Explicit role paths are used as supplied; they are not implicitly
rebased under `source`.

### Overlay rules

For `from_mapping_files()`:

1. validate the optional direct source directory;
2. use every explicit non-`None` role as the complete replacement for that
   role;
3. resolve omitted organism roles by their conventional names under `source`;
4. do not rediscover an explicitly provided role;
5. validate the final role inventory and reject one physical file assigned to
   multiple roles; and
6. require at least one organism role.

A file-factory profile may be partial with or without `source`. Missing roles
become unavailable capabilities. A provided path that is missing, not a regular
file, or otherwise invalid is an error; it never means “fall back to
discovery.”

For `from_mapping_directory()`:

- organism files are discovered only by fixed names inside each selected or
  enumerated organism directory;
- `organism_list` and `ko_pathway` explicitly replace their corresponding
  global conventional files;
- an omitted global role is discovered only at
  `source/organism/list_organism.tsv` or `source/ko/ko_pathway.tsv`;
- a missing auto-discovered global file means that capability is unavailable;
- a provided global path that is missing is an error.

`release_version` is exclusively caller-declared. Neither factory infers it
from a directory component, basename, modification time, `manifest.lock`, or
any other adjacent file.

### Multi-organism discovery

Construction validates and retains the direct root but does not enumerate it.
Each execution uses one top-level directory enumeration with these rules:

- organism directory names match `^[a-z]{3,4}$`;
- accepted organism codes are processed in lexical order;
- `ko` and `organism` are reserved global directories;
- other top-level directories produce one aggregated warning;
- top-level files are ignored;
- internal directory symlinks are not followed;
- the explicitly supplied source root itself may be a symlink;
- traversal is never recursive.

Every discovered organism must have the rectangular five-role profile:

```text
gene_list.tsv
conv_uniprot.tsv
conv_ncbi_geneid.tsv
gene_ko.tsv
gene_pathway.tsv
```

An existing zero-byte file satisfies its role and yields an observed empty
relation. A missing role is an `IntegrityError` for that execution. There is no
`skip_bad_organisms` or non-strict mode. An execution that discovers no
organism directories also fails rather than publishing an ambiguous empty
catalog.

The directory need not be a closed or complete KEGG release. If it contains 200
valid organism directories, an unscoped publication contains those 200. The
meaning is “all organisms available to this build,” not “all organisms known by
KEGG.”

## Organism Scope

`KEGGDatabase.with_organisms(organism_codes)` returns a lightweight mapping
handle with a normalized, unique organism-code scope. It does not scan source
directories. Codes are trimmed, must already match `^[a-z]{3,4}$`, and are
deduplicated and sorted. Empty input or invalid case/grammar raises
`ValueError`; bioextract does not silently rewrite organism codes.

The scope applies to organism-specific relations:

- `organisms()`;
- `gene_annotations()`;
- `gene_pathways()`;
- `gene_pathways_via_ko()`; and
- mapping selections and their unmatched decisions.

Global `ko_annotations()` and `ko_pathways()` remain global because a KO can be
shared by many organisms.

Source execution behaves as follows:

- a scoped handle opens only the selected organism directories and therefore
  provides physical pruning;
- an unscoped handle enumerates the direct root once and uses the organism
  directories available to that execution;
- a selected organism directory that is absent or becomes unreadable raises
  `IntegrityError` during execution.

Publication behavior is fixed at build time:

- writing an unscoped handle publishes all organism directories found by that
  build;
- writing a scoped handle publishes only the selected organism and gene rows;
- global `ko_annotation` remains complete for the supplied global capability;
- exact published members are the rows of `organism`;
- metadata records
  `bioextract.organism_scope_mode="selected"` or
  `"all_available_at_build"` and does not duplicate the member list.

A reopened publication can be narrowed to a subset of its `organism` rows but
cannot be expanded. Requesting an absent member raises `CapabilityError`.
There is no `with_all_organisms()`: the unscoped handle already represents all
members available to its source or publication.

## Fixed Publication Schema

All mapping publications contain exactly three physical biological tables,
including partial file-factory publications. Capability metadata distinguishes
“unavailable” from an observed empty relation.

### `organism`

| Position | Column | DuckDB/Polars type |
| ---: | --- | --- |
| 1 | `organism_code` | `String` |
| 2 | `genome_id` | `String?` |
| 3 | `organism_name` | `String?` |
| 4 | `taxonomy_lineage` | `List[String]?` |

`organism` contains exactly the organism members represented by the published
profile, whether they came from discovered directories or one explicit
file-factory handle. It does not copy every row from an optional organism list.

### `gene_annotation`

| Position | Column | DuckDB/Polars type |
| ---: | --- | --- |
| 1 | `organism_code` | `String` |
| 2 | `kegg_gene_id` | `String` |
| 3 | `gene_type` | `String?` |
| 4 | `genomic_position` | `String?` |
| 5 | `gene_symbol` | `String?` |
| 6 | `gene_aliases` | `List[String]?` |
| 7 | `gene_description` | `String?` |
| 8 | `uniprot_mappings` | `List[Struct{uniprot_id: String}]?` |
| 9 | `ncbi_gene_mappings` | `List[Struct{ncbi_gene_id: String}]?` |
| 10 | `ko_mappings` | `List[Struct{ko_id: String}]?` |
| 11 | `pathway_mappings` | `List[Struct{kegg_pathway_id: String, pathway_map_id: String}]?` |

The gene universe is the union of gene IDs observed in every provided organism
role. It is not limited to `gene_list.tsv`.

### `ko_annotation`

| Position | Column | DuckDB/Polars type |
| ---: | --- | --- |
| 1 | `ko_id` | `String` |
| 2 | `pathway_mappings` | `List[Struct{kegg_pathway_id: String, pathway_namespace: String, pathway_map_id: String}]?` |

The KO universe is the union of KO IDs observed in organism `gene_ko` roles and
the optional global KO-pathway file. When the global capability is absent,
gene-observed KOs remain present with null `pathway_mappings`.

### Null and empty semantics

The nested fields use one uniform capability rule:

- `null` means the source role required to know that field was unavailable;
- `[]` means the role was available and no value was observed for that entity;
- a non-empty list contains the complete distinct observed values for that
  entity.

Examples:

- omitted `gene_ko` -> every gene's `ko_mappings` is null;
- present zero-byte `gene_ko` -> every gene's `ko_mappings` is `[]`;
- present `ko_pathway` with no row for one gene-observed KO -> that KO's
  `pathway_mappings` is `[]`;
- omitted `organism_list` -> organism metadata and `taxonomy_lineage` are null;
- present list missing one published organism -> keep the organism row with
  null scalar metadata, `taxonomy_lineage=[]`, and one warning.

Scalar gene fields are null when no metadata row exists. When `gene_list` is
available but a gene appears only in another role, `gene_aliases=[]`. When the
whole capability is unavailable, `gene_aliases` is null.

### Capability metadata

Every mapping publication contains exactly these resource capability keys with
lowercase `"true"` or `"false"` values:

```text
bioextract.capability.gene_list
bioextract.capability.uniprot_conversion
bioextract.capability.ncbi_gene_conversion
bioextract.capability.gene_ko
bioextract.capability.gene_pathway
bioextract.capability.organism_list
bioextract.capability.ko_pathway
```

Missing, unknown, or non-boolean capability values are invalid. Physical table
presence does not imply capability. A specialized method whose required
capability is false raises `CapabilityError`; source-backed errors occur when
the lazy plan executes, while reopened publications can reject from embedded
capabilities.

The publication identity is:

```text
bioextract.resource_name = "kegg"
bioextract.resource_schema_version = "kegg-mapping-v1.0"
bioextract.source_schema_profile = "kegg-organism-mapping-files-v2"
bioextract.scope = "mapping"
bioextract.metadata_schema_version = "2"
```

`bioextract.release_version` is present only when the caller supplied
`release_version`.

## Parsing And Identifier Contract

All files are UTF-8, tab-separated, headerless text. Blank lines are ignored.
Non-blank rows require the exact role-specific column count. Parse and
integrity errors identify the logical source, display path, and one-based source
line.

### Organism roles

| Role | Input columns | Normalized relation |
| --- | --- | --- |
| `conv_uniprot.tsv` | UniProt xref, KEGG gene | gene -> UniProt |
| `conv_ncbi_geneid.tsv` | NCBI Gene xref, KEGG gene | gene -> NCBI Gene |
| `gene_ko.tsv` | KEGG gene, KO xref | gene -> KO |
| `gene_pathway.tsv` | KEGG gene, organism pathway xref | gene -> direct organism pathway |
| `gene_list.tsv` | KEGG gene, gene type, genomic position, display text | gene attributes |

`gene_list.tsv` is parsed as four columns:

1. `kegg_gene_id`;
2. `gene_type`;
3. `genomic_position`, retained as an opaque string; and
4. display text.

Display text is split at most once on the first semicolon:

- with a semicolon, the left side is split on commas; the first non-empty name
  is `gene_symbol`, remaining names are deduplicated and lexically sorted into
  `gene_aliases`, and the trimmed right side is `gene_description`;
- without a semicolon, the complete trimmed text is
  `gene_description`, `gene_symbol` is null, and `gene_aliases=[]`.

`genomic_position` is never parsed into coordinates because observed values
include forms such as `1`, `190..255`, and
`I:complement(...)`.

### Global roles

`organism/list_organism.tsv` has:

```text
genome_id<TAB>organism_code<TAB>organism_name<TAB>taxonomy_lineage
```

Taxonomy is split on semicolons, trimmed, and kept in source hierarchy order.
The list is left-joined only to the organism members actually being published.
Extra list rows are ignored. Conflicting duplicate metadata for one organism
is an `IntegrityError`. No NCBI taxonomy identifier is inferred.

`ko/ko_pathway.tsv` contains KO-to-pathway edges. Both observed pathway
namespaces are retained:

```text
ko:K00001<TAB>path:map00010
ko:K00001<TAB>path:ko00010
```

Both rows have `pathway_map_id="map00010"` but retain distinct
`kegg_pathway_id` and `pathway_namespace` values.

### Canonical identifiers

External response prefixes are removed:

```text
up:P12345          -> P12345
ncbi-geneid:1      -> "1"
ko:K00001          -> K00001
path:hsa00010      -> hsa00010
path:map00010      -> map00010
path:ko00010       -> ko00010
```

`kegg_gene_id` remains namespaced, for example `hsa:1`. Identifiers remain
strings; NCBI values are not coerced to integers, leading zeroes are not
discarded, and identifier case is not rewritten.

The parser enforces:

- KEGG gene IDs use exactly the current organism prefix;
- organism gene-pathway targets use that organism prefix plus five digits;
- KO IDs match `K` plus five digits;
- global KO-pathway targets use `map` or `ko` plus five digits;
- UniProt conversion prefixes are non-empty but are not restricted by a
  fragile accession regex;
- NCBI Gene suffixes are non-empty digits;
- organism genome IDs match `T` plus digits.

A cross-organism prefix mismatch is an `IntegrityError` whose stable diagnostic
context identifies the logical role, source path when known, and cause. Line,
byte-offset, raw-row, and scheduling-order details are best effort. One external
identifier mapping to multiple genes is legal.

### Duplicate and ordering semantics

Exact duplicate mapping edges are idempotent input and are removed silently.
Conflicting duplicate metadata remains fatal; diagnostics do not emit one
message per duplicate row.

Nested biological lists have set semantics:

- exact duplicate structs are removed;
- structs are sorted lexically by their declared fields;
- gene aliases are deduplicated and lexically sorted;
- `taxonomy_lineage` alone preserves hierarchy order.

Sorting is local to one entity's list. The implementation must not add a global
sort over all expanded edges merely to obtain deterministic presentation.
Top-level `LazyFrame` row order is not a caller contract; callers may add
`.sort()` when presentation requires it.

## Relationship Semantics

The publication stores only direct observations:

- gene -> pathway from `gene_pathway.tsv`;
- gene -> KO from `gene_ko.tsv`; and
- KO -> pathway from `ko_pathway.tsv`.

Direct gene pathways are never augmented with gene -> KO -> pathway results.
That traversal is a separate domain relation:

```text
gene_pathways_via_ko()
```

It retains the mediating `ko_id` so callers can audit why a gene acquired a
pathway. There is no `include_inferred` flag because a boolean would conflate
two relations with different evidence semantics.

The plan does not store normalized edge tables alongside the aggregate tables.
Callers can recover edges lazily:

```python
flat_gene_pathway = (
    db.gene_pathways()
    .explode("pathway_mappings")
    .unnest("pathway_mappings")
)
```

If a measured reverse lookup later justifies a physical acceleration table, it
is added narrowly and without changing the domain API. The initial publication
does not duplicate all normalized relations “just in case.”

## Public Lazy Relation API

Mapping-mode database methods are:

```python
db.organisms()
db.gene_annotations()
db.ko_annotations()
db.gene_pathways()
db.ko_pathways()
db.gene_pathways_via_ko()
db.select_ids(ids, *, namespace=...)
db.select_groups(ids_by_group, *, namespace=...)
```

Selection methods are:

```python
selection.matches()
selection.gene_annotations()
selection.gene_pathways()
selection.gene_pathways_via_ko()
selection.unmatched_ids()
```

Every tabular method above returns `pl.LazyFrame`. Selection construction and
`with_organisms()` return lightweight immutable behavior objects. The old
`mappings()` method, wide `mapping` table, `extract_*` names, `normalized=`
switches, and `explode=` switches are removed without aliases.

Mapping-mode `build_tidy()` is removed from the supported path because a
generic collection of independently executed lazy frames would reread the
source. `write_duckdb()` uses the staged coordinator defined below. Existing
BRITE behavior remains owned by the BRITE mode.

### Relation schemas

`gene_pathways()`:

```text
organism_code
kegg_gene_id
pathway_mappings List[Struct{
  kegg_pathway_id: String,
  pathway_map_id: String
}]
```

`gene_pathways_via_ko()`:

```text
organism_code
kegg_gene_id
pathway_mappings List[Struct{
  ko_id: String,
  kegg_pathway_id: String,
  pathway_namespace: String,
  pathway_map_id: String
}]
```

`ko_pathways()`:

```text
ko_id
pathway_mappings List[Struct{
  kegg_pathway_id: String,
  pathway_namespace: String,
  pathway_map_id: String
}]
```

`organisms()`, `gene_annotations()`, and `ko_annotations()` match their fixed
physical table schemas. Domain projections retain a nested list rather than
defaulting to one row per edge.

### Selection matching

`select_ids()` accepts exactly:

```text
"kegg_gene"
"uniprot"
"ncbi_gene"
```

KO and pathway selection are future explicit `select_kos()` or
`select_pathways()` APIs if justified; they are not overloaded into the
gene-identifier selector.

`matches()` is the normalized caller-to-gene lineage:

```text
# single selection
input_id
input_namespace
organism_code
kegg_gene_id

# grouped selection
group_id
input_id
input_namespace
organism_code
kegg_gene_id
```

One input may match several genes and species. The composite gene key is always
`(organism_code, kegg_gene_id)`. An unscoped multi-organism selection is legal
and retains all matches; callers who know their species should use
`with_organisms()` for physical pruning and unambiguous scope.

UniProt selection requires `uniprot_conversion` and NCBI Gene selection
requires `ncbi_gene_conversion`. KEGG gene selection uses the union gene
universe and therefore works when any organism role is available. A missing
namespace capability raises `CapabilityError` for matching and unmatched
relations; it does not classify every input as unmatched.

Selection annotation and pathway methods return one row per matched gene, not
one row per input-to-gene-to-annotation combination. Immediately after
`kegg_gene_id` they add:

```text
inputs List[Struct{
  input_id: String,
  input_namespace: String
}]
```

Grouped selection additionally places `group_id` first inside each input
struct. The input structs are non-empty, unique, and deterministically sorted.
If the same pathway is reached through different KOs, the via-KO result retains
both evidence structs.

`gene_pathways()` requires `gene_pathway`. The via-KO method requires both
`gene_ko` and `ko_pathway`. Capability failures never degrade to misleading
empty results.

`unmatched_ids()` is computed after organism scoping:

```text
# single
input_id

# grouped
group_id
input_id
```

### Input normalization

Selection construction eagerly consumes the caller iterable into a normalized,
immutable, deduplicated, sorted input relation so the returned lazy plans remain
replayable after the original iterator or selection variable is gone. This is
`O(unique input IDs)` caller state, not biological expansion, and has no hidden
input limit.

Normalization is namespace-aware:

- trim surrounding whitespace and drop blank values;
- UniProt accepts pipe form such as `sp|P12345|NAME` and keeps `P12345`;
- UniProt optionally strips `up:`;
- NCBI Gene optionally strips `ncbi-geneid:` and preserves the remaining
  string, including leading zeroes;
- KEGG gene requires a full organism prefix and never infers one from scope;
- an explicit prefix belonging to another namespace raises `ValueError` rather
  than silently missing.

The initial implementation does not add a `select_frame()` API.

### Caller usage

```python
from bioextract import KEGGDatabase

db = KEGGDatabase.from_mapping_directory(
    "/data/kegg/mapping/2026-06/raw",
    release_version="2026-06",
)
hsa = db.with_organisms(["hsa"])

# No source file is opened yet.
gene_lf = hsa.gene_annotations()
direct_pathway_lf = hsa.gene_pathways()

# Native Polars owns execution and output materialization.
gene_df = gene_lf.collect()
direct_pathway_lf.sink_parquet("hsa-gene-pathways.parquet")

# Flatten only when the caller explicitly needs one row per edge.
flat_pathway_lf = (
    direct_pathway_lf
    .explode("pathway_mappings")
    .unnest("pathway_mappings")
)

selection = hsa.select_ids(
    ["sp|P12345|EXAMPLE", "Q9Y243"],
    namespace="uniprot",
)
matched_gene_lf = selection.gene_annotations()
unmatched_lf = selection.unmatched_ids()
```

No `with` context is needed. The lazy frame owns a replayable query
description, not an open cursor. `connect()` remains the separate
caller-owned, read-only SQL escape hatch for reopened publications.

## Lazy Execution And Source Lifetime

Calling a relation method or `collect_schema()` must not enumerate organism
directories or open biological files. Every Polars execution creates fresh
readers and closes them on success, failure, cancellation, and early stop.

The source iterator is organism-major:

```text
resolve execution scope
  -> select or enumerate organism codes
  -> open one organism's required role files
  -> parse, validate, deduplicate, and aggregate that organism
  -> emit bounded Arrow/Polars batches
  -> release organism-local state
  -> continue to the next organism
```

Peak resident memory should therefore follow the largest organism plus bounded
in-flight execution state, not the total number of organisms or the Cartesian
edge count.

`with_organisms()` is the supported directory-pruning contract. A caller-added
`.filter(pl.col("organism_code") == "hsa")` is semantically correct, but the
initial adapter does not promise to reverse an arbitrary predicate into source
directory pruning. Projection and slice handling must remain correct, and early
termination must release current readers. The initial implementation need not
promise role-level source pruning from arbitrary projections.

The root and explicit source paths are retained, but their contents are live.
A lazy frame collected twice may observe caller changes made between
executions. The caller must not mutate files during one execution. bioextract
does not pre-freeze directory membership, record an expected-file manifest,
perform before/after drift scans, or claim snapshot isolation.

For one unscoped publication build, the single top-level enumeration creates
that execution's work queue. This is not a preflight release manifest; it is
ordinary bounded execution. Files added or removed concurrently are outside the
bioextract consistency guarantee and may cause an integrity failure.

## Staged DuckDB Publication

The mapping publisher must not execute `organisms()`,
`gene_annotations()`, and `ko_annotations()` independently because that would
repeat discovery and independently materialize the same relationships.

Implement one KEGG-specific multi-output coordinator that reuses shared atomic
destination, metadata-v2, and validation helpers:

1. prepare a target-adjacent staging DuckDB;
2. create metadata tables and the fixed three biological tables;
3. resolve the scoped or unscoped logical input inventory once;
4. register a private `input_file(logical_name, organism_code, role,
   source_path)` relation, including present zero-byte inputs;
5. bulk-scan each role's scan-eligible explicit path list with DuckDB using a
   fixed all-string schema and explicit TSV dialect, retaining the virtual
   filename for the join back to `input_file`;
6. retain bounded reject evidence, fail if any reject exists, validate
   biological keys with set queries, silently deduplicate exact relations, and
   reject conflicting metadata;
7. pre-aggregate each many-side role before joining and append complete
   organism/key-bounded partitions to `organism` and `gene_annotation`;
8. build the observed KO universe in private staging state, then bulk-scan the
   optional global KO-pathway role and append `ko_annotation`;
9. record resolved source membership with nullable observed bytes and only
   pre-existing trustworthy digests; do not add a provenance-only content or
   `stat()` pass;
10. remove internal staging relations, validate table and capability invariants,
    and `CHECKPOINT`;
11. close the writer, reopen the stage read-only, and validate again; and
12. atomically replace the destination.

Do not generalize a shared multi-output writer until a second resource proves
the same lifecycle. The KEGG coordinator should reuse protocol primitives, not
copy the metadata or atomic-replacement implementation.

Per-organism transfer Parquet files are not created. The P3 candidate uses
native DuckDB scans and bulk `CREATE ... AS SELECT` / `INSERT ... SELECT`
operations. Explicitly configure and record DuckDB threads, memory limit,
temporary directory, and temporary-size limit. Complex `list` aggregate state
is not assumed to obey the buffer-manager limit, so final nested aggregation
remains organism/key partitioned and process RSS must demonstrate a plateau.

DuckDB transaction and aggregation windows are internal durability and memory
mechanisms:

- do not hold one huge transaction for the entire release;
- do not autocommit every row;
- keep partial staging commits invisible because the stage is not the
  destination;
- expose no public transaction or batch-size tuning parameter.

The physical layout is clustered by:

```text
organism:       organism_code
gene_annotation: organism_code, kegg_gene_id
ko_annotation:   ko_id
```

Organism-major insertion and key-local aggregation should preserve useful
DuckDB zonemaps. Do not add ART indexes initially: they are secondary physical
copies, add build memory and size, and do not index elements inside nested
lists.

Source logical names are:

```text
organism/{organism_code}/gene_list
organism/{organism_code}/uniprot_conversion
organism/{organism_code}/ncbi_gene_conversion
organism/{organism_code}/gene_ko
organism/{organism_code}/gene_pathway
global/organism_list
global/ko_pathway
```

Every resolved available role has one `_bioextract.source_file` row, including
a zero-byte file that emits no CSV row. This is a declarative input inventory,
not a physical I/O trace: an engine may reopen or reorder fragments without
changing publication identity. Recording roughly one row per resolved file is
acceptable and auditable; metadata v2 avoids duplicating those rows in one JSON
value. There is no per-element source path or line duplication inside
biological nested structs.

## Validation And Failure Semantics

Zero-byte files are valid observed-empty inputs and blank lines are ignored.
Exact duplicate edges are deduplicated silently.

The following fail fast with `IntegrityError`:

- malformed column counts;
- invalid UTF-8;
- empty required identifiers;
- invalid namespace or identifier grammar;
- a gene or pathway prefix that conflicts with the current organism;
- conflicting duplicate gene metadata;
- conflicting duplicate organism metadata;
- missing rectangular organism files in a directory build; and
- source content that changes enough during an execution to make parsing or
  cross-file validation inconsistent.

Source-backed lazy relations raise when executed. A publication build discards
its staging database on any parser, validation, interruption, or cancellation
failure and preserves an existing destination. Standard Python logging reports
organism progress and aggregated warnings; there is no public `progress=`
callback in the first version.

bioextract validates the content it reads. It does not guarantee that a caller
keeps the surrounding directory stable.

## Performance And Benchmark Gates

### Fixed-scope publisher benchmark

The earlier 11,782-organism attempt is the sole full-source development run.
P3 decisions use the exact 100- and 1,000-organism scopes defined by the
performance plan; the 1,000-organism scope is guarded by its organism-list
SHA-256, which is benchmark identity rather than source-content provenance.

Before replacing the P1 publisher:

1. reconcile compact fixtures and the fixed 100-organism scope;
2. run at least two ordinary local fixed-1,000 builds, adding a third only when
   variance can change the verdict;
3. record wall and CPU time, process RSS series and peak, open-file descriptors,
   DuckDB resource settings, peak spill/temp bytes, output bytes, table row
   counts, capabilities, input membership, and reject counts;
4. explode the aggregate fields and reconcile deterministic normalized and
   direct-edge checksums with the P1 reference;
5. inject rejects, validation failures, interruption, and cancellation and
   verify stage/spill cleanup plus prior-target preservation; and
6. accept the DuckDB candidate only when end-to-end median wall time improves
   by at least 15%, peak RSS is no more than 20% above the 2.88-GiB P1 local
   reference and plateaus, and every biological check is identical.

Acceptance is structural:

- RSS reaches a bounded plateau rather than growing approximately linearly with
  processed organism count;
- open file descriptors remain bounded;
- output contains every valid source edge without hidden limits;
- no wide cross-product appears internally or physically;
- list aggregation is local to one organism/gene/KO working set.

The benchmark record preserves input identity, package/dependency versions,
command, environment, engine settings, and output checksums. Physical file
read count, open order, and error order may be measured diagnostically but are
not acceptance contracts.

After one candidate is frozen, a complete build requires a separate
release-readiness decision, an offline window projected from fixed-scope
evidence, enough stage and spill capacity, and live RSS/FD/temp monitoring. It
must not be triggered by ordinary testing or tuning.

### Reader scheduling decision

Complete-parser Python concurrency is closed after it regressed both wall time
and RSS on the fixed 100-organism scope. The DuckDB scanner owns file scheduling
and readahead during P3; bioextract adds neither a second Python prefetch layer
nor a public `max_workers` knob. Any future concurrency change requires new
fixed-scope end-to-end evidence rather than role-only throughput.

### Reverse lookup gate

Aggregated storage may make external-ID-to-gene lookup scan nested values. Do
not preemptively duplicate every edge. Benchmark:

- human UniProt selections of 1, 100, and 10,000 IDs;
- human NCBI Gene selections of 1, 100, and 10,000 IDs;
- human plus mouse;
- an unscoped 100-ID workload;
- cold and warm runs.

Record wall time, CPU time, peak RSS, input/match/unmatched counts, checksum,
query plan, and scanned rows. Compare against a temporary normalized lookup
baseline used only by the benchmark.

The accepted three-table schema is not changed inside the benchmark. If the
recorded serving path shows an order-of-magnitude degradation or misses an
explicit downstream operational budget, stop release acceptance and open a
separately reviewed schema amendment. The only candidate initial acceleration
table is:

```text
organism_code
input_namespace
input_id
kegg_gene_id
```

It would remain an internal physical detail and would not change the public
selection API, but its addition still requires an explicit publication-schema
decision and updated table-inventory tests.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| Small-file metadata operations dominate runtime | One bounded logical inventory, native role-level multi-file scans, no recursive pre-stat or provenance-only hash pass. |
| Aggregate lists hide incomplete capabilities | Exact boolean capability keys plus null/unavailable and empty/observed semantics. |
| Aggregate storage slows reverse lookup | Benchmark real selection workloads; add only the narrow lookup table when evidence crosses the acceptance gate. |
| Nested aggregation creates one large per-organism spike | Process organism-major, aggregate locally, measure the largest organism, and release state before continuing. |
| Concurrent source mutation causes inconsistent output | Caller owns immutability; fail on observed integrity violations and never claim snapshot isolation. |
| Global KO data is accidentally truncated by species scope | Scope only organism/gene relations; retain complete supplied global KO data. |
| Direct and inferred pathways are conflated | Separate methods and schemas; no boolean mode or implicit union. |
| Deterministic sorting becomes a full-build cost | Sort only local nested sets; do not promise top-level row order. |
| Source and publication drift semantically | One schema fixture and source/reopened parity tests for every domain relation. |
| Metadata migration hides KEGG review | Land metadata v2 independently, then implement KEGG against the accepted shared contract. |
| Old downstream SQL depends on `mapping` | Intentional pre-v1 rebuild and public-API migration; no private-table compatibility promise. |
| Formal data is replaced prematurely | Candidate target and downstream validation first; formal CephFS replacement requires explicit release authority. |

## External Design Basis

The plan relies on native engine capabilities rather than a bioextract-specific
execution facade:

- [Polars LazyFrame API](https://docs.pola.rs/api/python/stable/reference/lazyframe/index.html)
  for deferred composition and native execution terminals;
- [Polars list expressions](https://docs.pola.rs/user-guide/expressions/lists-and-arrays/)
  for explicit nested manipulation;
- [DuckDB LIST](https://duckdb.org/docs/current/sql/data_types/list) and
  [STRUCT](https://duckdb.org/docs/stable/sql/data_types/struct) for retained
  aggregate relationships;
- [DuckDB aggregate ordering](https://duckdb.org/docs/lts/sql/functions/aggregates)
  for deterministic local list construction;
- [DuckDB multi-file scans](https://duckdb.org/docs/current/data/multiple_files/overview)
  for explicit fragment lists and filename lineage;
- [DuckDB faulty-CSV handling](https://duckdb.org/docs/current/data/csv/reading_faulty_csv_files)
  for bounded reject evidence without accepting malformed input;
- [DuckDB import guidance](https://duckdb.org/docs/guides/import/overview)
  for scanner/set-based loading instead of row-at-a-time inserts;
- [DuckDB workload tuning](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads)
  for spill-aware execution and the documented qualification that complex
  aggregate state requires process-level memory observation;
- [Apache Arrow Dataset](https://arrow.apache.org/docs/cpp/api/dataset.html)
  for the distinction between logical input fragments and physical scan
  scheduling;
- [DuckDB bulk insertion guidance](https://duckdb.org/docs/lts/data/insert),
  [checkpoint](https://duckdb.org/docs/current/sql/statements/checkpoint), and
  [index behavior](https://duckdb.org/docs/current/sql/indexes) for the staged
  physical design; and
- the [KEGG API format reference](https://www.kegg.jp/kegg/rest/keggapi.html)
  for official `list`, `link`, and `conv` response semantics.
