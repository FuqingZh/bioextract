# bioextract v1.0 Publication Inspection Implementation Plan

Version: v1.0
Date: 2026-08-04
Status: current
Authority: [Domain Access Architecture](../architecture/20260729-v1.0-domain-access-architecture.md) and [Materialized Dataset Contract](../architecture/tidy-dataset-contract.md)

## Goal

Add a narrow, read-only API that inspects exactly one caller-supplied local
bioextract DuckDB publication and returns its validated publication and
provenance records.

The API is not publication discovery. `bioextract` accepts one explicit path,
validates the embedded metadata-v1 contract, returns deterministic immutable
records, and closes its DuckDB connection. It neither locates publications nor
decides which publications a caller should inspect.

## Settled Boundary

`bioextract` owns inspection of one explicit local publication path. It has no
dependency on `biofetch`, `bioinfo`, schedulers, or downstream applications.
It does not scan directories or define a manifest, catalog, serialization
format, discovery rule, or skip policy.

Future external `bioinfo` code or scripts may enumerate paths and call the API
once per path. That external layer owns any catalog format, aggregation,
serialization, path-discovery behavior, and operational policy; none of those
choices become a `bioextract` contract.

The stable API is:

```python
bioextract.inspect_publication(
    path,
    *,
    verify_table_counts=False,
) -> PublicationInspection
```

`inspect_publication` is a lazy top-level export. The stable
`bioextract.publication` module owns the function, `PublicationInspection`,
and its supporting public result-record types. Supporting records are not
flattened into the top-level package.

## Validation Contract

Inspection opens the supplied DuckDB publication read-only and guarantees
connection closure on success and failure. It reuses the metadata-v1 validator
owned by `src/bioextract/_publication.py` rather than introducing a second
interpretation of publication metadata.

By default, inspection validates:

- metadata schema v1;
- exactly the five required `_bioextract` provenance tables and their schemas:
  `metadata`, `source_file`, `table_info`, `column_mapping`, and
  `validation_issue`;
- parity between normalized embedded metadata and the `metadata` table;
- parity between the embedded source inventory and `source_file`;
- parity between validation metadata and `validation_issue`; and
- parity between `table_info` table names and the biological tables in
  `main`.

Default inspection does not dispatch to a resource reader, validate a
resource's biological schema, infer identity from a path or filename, check
whether recorded source files still exist, hash source files, mutate the
publication, or scan domain rows. In particular, it does not execute domain
table `count(*)` queries.

When `verify_table_counts=True`, inspection additionally executes `count(*)`
for each recorded biological table and verifies the result against
`_bioextract.table_info`. This is an explicit, potentially expensive integrity
check rather than default inspection behavior.

An invalid or unreadable publication raises `bioextract.errors.IntegrityError`
with actionable path and validation context and preserves the underlying
failure as its cause. The result exposes no `sql`, `query`, or `connect`
escape hatch.

## Result Contract

`PublicationInspection` and every supporting record are immutable and use
slots. The result contains publication identity, version, and validation
metadata together with deterministic collections for:

- metadata entries;
- biological table records;
- source-file records;
- column-mapping records; and
- validation-issue records.

Ordering is defined and deterministic so equivalent publications produce
equivalent inspection results independent of DuckDB's incidental row order.
Records retain provenance display paths exactly as published. Neither the
publication path nor a catalog supplies or overrides resource, release,
schema, or source identity.

The detailed field names and scalar types will be fixed by contract tests in
the implementation PR. They must represent the existing metadata-v1 values
without changing the five provenance schemas or any resource publication
schema.

## Delivery Phases

### Phase 1: Documentation plan

Land this document and its `docs/README.md` navigation entry as a docs-only PR
from current `origin/main`. This phase changes no code, tests, data, CephFS
publication, or existing pull request.

### Phase 2: Narrow API implementation

Close or supersede draft PR #26, then implement the inspection API fresh from
the then-current `main`. PR #26 mixes `biofetch`/catalog responsibilities with
the library API and refers to superseded test paths, so it must not merge as
is. Closing or superseding it is a Phase 2 action, not a mutation performed by
this documentation PR.

Implementation stays within the single-publication boundary and reuses the
existing internal metadata-v1 validation path. It must not introduce catalog,
manifest, directory enumeration, or downstream integration behavior.

### Phase 3: Optional external catalog

If useful, a future external utility under `bioinfo/scripts` may enumerate
local publication paths, call `inspect_publication()` for each path, and own
catalog serialization. It is not a `bioinfo` package contract. This phase is
optional and outside the `bioextract` repository and compatibility contract.

## Compatibility

This is an additive API. Existing `XDatabase` constructors, selections,
connections, and all biological and `_bioextract` publication schemas remain
unchanged. Publication inspection does not become a prerequisite for existing
domain access.

The lazy top-level function is a compatibility promise and is the only new
top-level export alongside the 11 existing `*Database` classes.
`PublicationInspection` and all supporting result records are stable exports
only from `bioextract.publication`; none is flattened into `bioextract`. No
former PR #26 catalog or serialization shape is retained as a compatibility
surface.

## Verification And Acceptance

The implementation requires layered unit, contract, and integration coverage:

- immutable slotted records and deterministic ordering;
- lazy top-level export, stable module exports, exact call signature, and
  error taxonomy/cause chaining;
- valid and corrupt compact DuckDB fixtures;
- read-only opening and guaranteed connection closure on success and failure;
- metadata, source inventory, validation-issue, and `main`/`table_info` parity;
- proof that default inspection performs no biological row scan;
- opt-in count verification and a recorded-versus-actual count mismatch; and
- preservation of provenance display paths without path-derived identity.

Tests use temporary local fixtures. They do not rebuild snapshots or read or
write CephFS. On the exact implementation head, run focused tests while
iterating and the repository's canonical non-mutating gate:

```console
pdm run check
```

Acceptance also requires evidence that existing `XDatabase` APIs and
publication schemas are unchanged.

## Risks And Rollback

- **Validator divergence:** a second validator could accept a publication that
  resource readers reject. Reuse `_publication.py` and cover shared corrupt
  fixtures. Roll back the additive API if one validation contract cannot be
  maintained.
- **Accidental full scans:** default inspection could become proportional to
  domain row count. Assert executed-query behavior and reserve `count(*)` for
  `verify_table_counts=True`.
- **Leaked connections or write access:** failures could retain handles or
  mutate a publication. Exercise success and failure closure and verify
  read-only behavior.
- **Premature record compatibility:** underspecified or flattened records could
  constrain later catalog work. Keep supporting records in
  `bioextract.publication` and test their exact stable fields before release.
- **Scope regression toward PR #26:** discovery and catalog behavior could
  re-enter the library. Reject those changes or move them to an independent
  external Phase 3 change.

Rollback is deletion of the additive top-level export and
`bioextract.publication` API before release. No publication or resource schema
migration is needed, and existing DuckDB files remain valid.

## Completion

This plan is complete when:

1. the docs-only Phase 1 PR is merged;
2. PR #26 is closed or explicitly superseded without merging its mixed
   boundary;
3. a fresh implementation PR from current `main` lands the narrow API and all
   acceptance coverage;
4. focused tests and `pdm run check` pass on that exact implementation head;
5. exact-head CI and current-head review are clean with no actionable review
   threads; and
6. no snapshot rebuild, data mutation, or CephFS access occurred.

The optional external catalog in Phase 3 is not required for completion of the
`bioextract` API.
