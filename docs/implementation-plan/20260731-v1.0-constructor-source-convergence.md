# bioextract v1.0 Constructor Source Convergence

Version: v1.0
Date: 2026-07-31
Status: current
Authority: [Domain Access Architecture](../architecture/20260729-v1.0-domain-access-architecture.md)

## Goal

Converge public resource constructors on names that identify the caller-visible
logical source profile. A constructor for one primary representation names that
representation; a constructor for a homogeneous file profile uses the profile
name; and `from_files` is retained only when a heterogeneous bundle of named
file roles is itself the public contract.

The convergence is split into three independently reviewable phases:

1. Phase 1 establishes the naming contract and applies the low-risk eggNOG and
   STRING changes.
2. Phase 2 expands the WikiPathways GMT source resolver without moving
   resource-specific discovery out of the WikiPathways package.
3. Phase 3 unifies the three Rhea explicit-file constructors without changing
   publication or capability behavior.

Each phase removes its superseded public entrypoints directly. This is pre-1.0
contract convergence: there are no compatibility aliases or deprecation
warnings.

## Naming Contract

Constructor names describe the logical input contract rather than the number
of filesystem objects used internally:

- Use a representation-specific name such as `from_sqlite` when one primary
  logical representation defines the source, including when transport
  compression wraps it.
- Use an explicit homogeneous file-profile name when the accepted roles belong
  to one stable profile.
- Retain `from_files` only when the heterogeneous named file bundle is itself
  the contract.
- Use `source` when one parameter can resolve a file, directory, archive,
  sequence, or glob. Resolvers remain inside the package that owns the resource
  format.
- Record actual resolved files as provenance. Do not infer release versions
  from filenames or paths.

The following currently appropriate explicit file-profile names are frozen by
this plan:

- `ChEBIDatabase.from_table_files`
- `KEGGDatabase.from_mapping_files`
- `KEGGDatabase.from_metabolic_files`
- `InterProDatabase.from_mapping_files`

The following heterogeneous named bundles appropriately retain `from_files`:

- `ReactomeDatabase.from_files`
- `OmniPathDatabase.from_files`
- `STRINGDatabase.from_files`

Changing those frozen decisions requires a new public-contract decision rather
than incidental cleanup in one of these phases.

## Boundaries And Invariants

The owning resource packages under `src/bioextract/` retain source parsing,
resolution, biological semantics, staging, and provenance collection. The
shared tidy and publication contracts remain unchanged.

Across all three phases:

- package version and every resource schema remain unchanged;
- generated Parquet and DuckDB schemas remain unchanged;
- caller-supplied or resolved files, not path-derived guesses, are provenance;
- existing partial-resource capability behavior is preserved;
- no downloader or downstream-application dependency is introduced;
- tests use local temporary fixtures; and
- these code PRs perform no CephFS writes.

WikiPathways and Rhea implementation changes are explicit non-goals of Phase 1.
Phase 2 does not change Rhea. Phase 3 does not change publication schemas.

## Phase 1: Naming Contract And Low-Risk Convergence

### Public interfaces

Replace:

```python
EggNOGDatabase.from_files(
    *,
    eggnog_database=...,
    cog_functions=None,
    temp_dir=None,
)
```

with:

```python
EggNOGDatabase.from_sqlite(
    source,
    *,
    cog_functions=None,
    temp_dir=None,
)
```

`source` is an `os.PathLike[str] | str` path to an eggNOG mapper SQLite
database or its gzip-wrapped form. SQLite is the primary logical format in
both cases. `EggNOGDatabase.from_files` is removed and must be observably
absent.

Retain `STRINGDatabase.from_files`, because aliases and links are a
heterogeneous named bundle, but change its leading roles to:

```python
STRINGDatabase.from_files(
    *,
    aliases: os.PathLike[str] | str | None = None,
    links: os.PathLike[str] | str | None = None,
    rank_by_source=...,
    release_version=None,
)
```

Both roles become keyword-only. No STRING parsing, ranking, release validation,
selection, or output behavior changes.

### Implementation and documentation

Update all current eggNOG call sites, public docstrings, observable examples,
tests, and current documentation. Specifically update the root `README.md`,
the shared domain-access architecture, eggNOG architecture and testing
documents, this documentation index, and the completed domain-contract plan
with a historical follow-up note that points to this plan.

Preserve eggNOG parsing, optional COG enrichment, gzip decompression, temporary
staging, cached frames, selections, Parquet output, embedded provenance, and
all output schemas. Preserve the public docstring target count while replacing
the constructor target.

### Acceptance gate

Run:

```console
pdm run pytest tests/test_eggnog.py tests/test_stringdb.py tests/test_publication.py tests/test_docstring_examples.py
pdm run check
```

The focused tests must prove the new signatures, successful SQLite and
gzip-wrapped SQLite handling, keyword-only STRING roles, unchanged behavioral
outputs, unchanged docstring target count, and absence of
`EggNOGDatabase.from_files`.

Before delivery, search current source, tests, the root README, and current
documentation for stale Phase 1 names. Archived or superseded history may
retain a former name only when its historical status is explicit.

Phase 1 is one breaking-change PR and one focused conventional commit. It
targets `main` and does not include WikiPathways or Rhea code changes.

## Phase 2: WikiPathways GMT Source Resolution

Status: implemented on 2026-07-31 in the Phase 2 pull request.

Phase 2 depends on Phase 1's naming contract being merged. Replace the
single-path constructor with:

```python
WikiPathwaysDatabase.from_gmt(
    source,
    *,
    species=None,
    glob=True,
)
```

`source` supports one path, a sequence of paths, or a glob expression. The
WikiPathways package owns normalization, glob expansion, missing/empty-match
validation, and parsing. `glob=False` treats a string or path as a literal
path. A sequence is resolved element by element under the same rule.

The accepted multi-file semantics are:

- normalize every resolved input to its actual physical file and order those
  actual files deterministically before parsing;
- raise an error when the same physical file is reached twice, whether through
  repeated literals, overlapping globs, symlinks, or another resolution path;
- infer no release, species, Collection, Version, or other metadata from a
  filename or directory path;
- validate content across the resolved set and require one common official
  `Collection` value and one common official `Version` value;
- require `WikiPathwaysId` to be unique across the entire resolved dataset,
  raising an error for a duplicate within one GMT or across multiple GMTs
  instead of silently applying `unique()` or choosing one row;
- allow a single GMT file to contain rows for multiple species;
- retain `species=` as a row/content filter, without imposing a
  one-species-per-file or unique-species-per-file invariant; and
- record every normalized actual input file as provenance, regardless of
  species filtering or the number of rows that file contributes to the
  resulting dataset.

The output schemas and biological parsing contract remain unchanged.

### Acceptance gate

Focused WikiPathways tests must cover one literal path, a path sequence, glob
enabled and disabled behavior, deterministic resolution, invalid and empty
inputs, duplicate physical-file detection, common Collection and Version
validation, duplicate `WikiPathwaysId` rejection both within one GMT and across
GMTs, multiple species in one file, the `species=` row filter, provenance
containing every normalized actual input file including files whose rows are
entirely filtered out, and unchanged selection and publication schemas. Update
public API gates, docstring examples, root usage, architecture, and testing
documentation, then run `pdm run check`.

Phase 2 is a separate PR targeting `main`; it contains no Rhea changes and
performs no real snapshot or CephFS writes.

### Phase 2 evidence

- The public signature gate fixes `from_gmt(source, *, species=None,
  glob=True)`.
- Focused tests cover literal and glob resolution, deterministic actual-file
  ordering, every rejected source class, duplicate physical files, complete-set
  Collection/Version and pathway-ID validation, multi-species content,
  species filtering, and every-file provenance.
- The common Version derived from official GMT Collection content is published
  as `bioextract.release_version` with
  `bioextract.release_version_source=official_metadata`; focused DuckDB
  provenance assertions fix both values and forbid path-derived release
  identity.
- The focused WikiPathways, publication, and public-docstring gate and the
  repository-owned `pdm run check` gate are the delivery evidence recorded by
  the Phase 2 pull request.

## Phase 3: Rhea Explicit-File Consolidation

Phase 3 depends on the naming contract and may proceed after Phase 2 because
the public surfaces are independent. Remove:

- `RheaDatabase.from_reaction_files`
- `RheaDatabase.from_compound_files`
- `RheaDatabase.from_cross_reference_files`

and replace them with one keyword-only constructor:

```python
RheaDatabase.from_files(
    *,
    rdf=None,
    directions=None,
    relationships=None,
    obsolete_reactions=None,
    reaction_smiles=None,
    sdf=None,
    chebi_names=None,
    chebi_ph7_3_mapping=None,
    xrefs=None,
    uniprot_sprot=None,
    uniprot_trembl=None,
)
```

These are the existing 11 explicit logical roles. Each accepts
`os.PathLike[str] | str | None`. There are no old aliases and no compatibility
wrappers.

The unified constructor accepts any valid mixed partial capability profile,
including roles that previously belonged to different constructors. Validation
applies this exact matrix:

- at least one of the 11 roles is required;
- the reaction group is `rdf`, `directions`, `relationships`,
  `obsolete_reactions`, and `reaction_smiles`;
- supplying any reaction-group role requires both `rdf` and `directions`;
- compound roles (`sdf`, `chebi_names`, and `chebi_ph7_3_mapping`) remain valid
  independently of one another and of the reaction group;
- cross-reference roles (`xrefs`, `uniprot_sprot`, and `uniprot_trembl`) remain
  valid independently of one another and of the other groups; and
- one normalized physical file cannot fill more than one logical role.

Unavailable operations continue to raise the existing capability error. The
snapshot and provenance inventory retain each supplied role and actual file.

The snapshot `scope` value is determined only by the supplied role groups:

| Supplied role groups | `scope` |
| --- | --- |
| reaction only | `reactions` |
| compound only | `compounds` |
| cross-reference only | `cross_references` |
| two or three groups | `partial` |

`release` remains exclusive to `from_release`, and `publication` remains
exclusive to `from_duckdb`; `from_files` never assigns either value. `partial`
is a newly permitted value in the existing string metadata field. It does not
change the metadata field, resource tables, or publication schema and therefore
does not require a resource schema version change.

Rhea parsing, biological relationships, identifier namespaces, lazy selection,
partial publication, direction semantics, validation, DuckDB layout, metadata
schema, table schemas, and all extraction headers remain unchanged. In
particular, this phase makes no publication schema change.

### Acceptance gate

Focused Rhea tests must cover each role and the complete validation/scope
matrix: no roles rejected; every reaction-group role rejected without either
required `rdf` or `directions`; reaction-only, compound-only, and
cross-reference-only profiles assigned their exact group scope; every pair of
groups and all three groups accepted with `scope="partial"`; compound and
cross-reference roles accepted independently; and reuse of one physical file
across roles rejected. Tests must also cover absent old constructors, the exact
keyword-only signature, provenance, capability errors, `release` remaining
exclusive to `from_release`, `publication` remaining exclusive to
`from_duckdb`, acceptance of the new `partial` metadata value without a resource
schema version change, and byte/schema-level publication invariants where the
existing fixtures permit. Update public API gates, all observable examples,
architecture, and testing documentation, then run `pdm run check`.

Phase 3 is a separate breaking-change PR targeting `main` and performs no real
snapshot or CephFS writes.

## Risks, Rollback, And Cleanup

The primary risk is a stale caller using a removed constructor or positional
STRING role. Each phase controls that risk through repository-wide current-doc
and call-site searches plus explicit absence/signature tests. Because aliases
are intentionally forbidden, rollback is a normal revert of the owning phase,
not a compatibility layer.

Source-resolution expansion in Phase 2 risks ambiguous matches; deterministic
resource-local resolution and provenance assertions are its gate. Phase 3
risks accidentally coupling previously independent Rhea roles; mixed partial
capability tests and unchanged publication-schema assertions are its gate.

After each phase, remove superseded code paths, examples, and tests in the same
PR. Historical documents remain untouched unless they present a former
interface as current; in that case add an explicit follow-up or supersession
note rather than rewriting historical outcomes.

## Final Acceptance

The three-phase convergence is complete only when all three PRs have landed,
each old constructor is absent, current documentation exposes only the settled
interfaces, all focused gates pass, and `pdm run check` passes on each exact PR
head. Completion does not require or authorize a package-version change,
publication-schema migration, real snapshot build, CephFS write, or merge
outside the normal reviewed PR gates.
