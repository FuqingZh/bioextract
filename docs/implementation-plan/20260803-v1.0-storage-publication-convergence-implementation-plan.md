# bioextract v1.0 Storage And Publication Convergence Implementation Plan

Version: v1.0
Date: 2026-08-04
Status: complete
Authority: [Domain Access Architecture](../architecture/20260729-v1.0-domain-access-architecture.md)

## Goal

Converge bioextract on one clear storage boundary without forcing official
database releases into one physical format.

The stable product remains resource-specific domain access: identifier
resolution, biological relationships, hierarchy and direction semantics,
cross-file validation, grouped selection, and unmatched-input accounting.
Storage is an execution strategy:

- consume an official efficient representation directly when it already
  supports the intended domain access;
- materialize a source only when repeated parsing, joining, traversal, or
  formal distribution justifies a derived publication; and
- publish every bioextract-owned materialized database as one DuckDB file,
  whether it currently contains one relation or many.

The current architecture and resource documents now carry this contract.
Older implementation-plan storage statements are superseded; historical
decisions and benchmark measurements remain factual records and are not
rewritten.

## Accepted Decisions

### Direct access and materialization are capabilities

A resource does not need a writer merely because another resource has one.
The model has exactly two strategies:

| Strategy | Meaning | Current examples |
| --- | --- | --- |
| `official/native direct access` | The official representation is already suitable for the supported domain queries | eggNOG SQLite, STRING, OmniPath |
| `bioextract-owned DuckDB` | Repeated interpretation is expensive or relationally complex, so one DuckDB may be written per materialized logical product regardless of relation count | ChEBI, Rhea, GO, Reactome, WikiPathways, KEGG, InterPro, UniProt |

The state belongs to a logical source profile, not necessarily to the entire
upstream brand. UniProt idmapping and UniProtKB, for example, are separate
products even though one `UniProtDatabase` handle owns both profiles.

### DuckDB is the only bioextract publication container

Parquet is no longer a canonical bioextract publication. It remains available
as:

- an internal streaming transfer format while constructing DuckDB;
- a caller-owned export produced from an extracted Polars frame; or
- a caller-owned export produced through DuckDB `COPY`.

No canonical Parquet footer contract, sidecar manifest, or parallel
Parquet/DuckDB product is retained. A one-table DuckDB is valid and can gain
new tables later without changing the user-visible container or reopening
API.

### Public writer naming remains format-explicit

Materializable source handles expose:

```python
result = source.write_duckdb(path, if_exists="fail")
```

Published handles expose:

```python
database = XDatabase.from_duckdb(path)

with database.connect() as connection:
    relation = connection.sql("SELECT * FROM mapping")
```

`write_duckdb()` is retained instead of `write_database()`. DuckDB is a
physical compatibility contract, the name is symmetric with `from_duckdb()`,
and Polars uses `write_database()` for writing a DataFrame into a database
table rather than for creating a self-contained domain publication.

Every public writer requires an explicit destination. The library never
infers a filename. Within the versioned CephFS resource layout, the repository
convention is `tidy/data.duckdb`; callers outside that layout may choose any
`.duckdb` filename. The filename is not machine identity or a compatibility
contract.

### Every publication is both domain-accessible and natively queryable

If a resource profile exposes `write_duckdb()`, the same resource handle must
support `from_duckdb()` and a caller-owned read-only `connect()` connection.
The published handle must retain the same domain selection and extraction
semantics as the source adapter wherever both support the same capability.

Resource-domain convenience remains selection-first:

```python
selection = database.select_ids(ids, namespace=...)
selection = database.select_groups(ids_by_group, namespace=...)

df_entities = selection.extract_*()
df_unmatched = selection.extract_unmatched_ids()
```

Resource-specific entry names such as `select_compounds()` and
`select_reactions()` remain appropriate when they identify the selected
entity. Selections are deferred domain plans; `extract_*()` terminals return
eager Polars `DataFrame` objects. Grouped selection resolves each globally
unique normalized identifier once per Selection and then restores every
caller-owned `GroupId`.

Generic projection, filtering, aggregation, sorting, SQL, and caller-specific
Parquet export remain Polars or DuckDB responsibilities.

## Publication Metadata v1

Metadata v1 is the first and only supported publication metadata contract.
Legacy development metadata readers and dual-key compatibility have been
removed, and the maintained formal publications have passed rebuild
acceptance.

Every DuckDB publication contains biological relations in `main` and exactly
the bioextract-owned provenance relations below:

```text
_bioextract.metadata
_bioextract.source_file
_bioextract.table_info
_bioextract.column_mapping
_bioextract.validation_issue
```

The v1 metadata rules are:

- `bioextract.resource_schema_version` is required and versions the
  bioextract-owned biological output schema;
- `bioextract.source_schema_profile` is required and names a
  bioextract-owned parser profile whose required source structure has been
  validated from content;
- `bioextract.source_schema_version` is optional and is written only when the
  upstream source declares an authoritative schema label;
- `bioextract.release_version` is optional and is never inferred from paths,
  basenames, archives, timestamps, or modification times;
- `bioextract.release_version_source` occurs only with `release_version` and
  is either `caller` or `official_metadata`;
- the complete normalized physical source inventory is recorded in
  `_bioextract.source_file` and the canonical embedded inventory, with parity
  validation between them;
- `_bioextract.table_info` matches the actual domain table inventory and row
  counts;
- `_bioextract.validation_issue` always exists, including when empty, and its
  count determines `passed` versus `passed_with_warnings`; and
- unknown, legacy, or physically incomplete metadata contracts are rejected.

Direct adapters do not modify an official database to embed these relations.
They validate and retain source identity on the handle; `_bioextract` belongs
only to bioextract-owned DuckDB publications.

of optional source roles contains only supported domain tables and declares
its capability inventory; it does not create misleading empty observations or
switch back to Parquet.

## eggNOG Direct-Access Contract

The primary interface remains:

```python
database = EggNOGDatabase.from_sqlite(
    source,
    *,
    cog_functions=None,
    temp_dir=None,
)
```

The v1 behavior is:

- a plain `.db` source is queried directly;
- a `.db.gz` source is accepted as a convenience input but must be fully
  decompressed to temporary storage before SQLite access;
- `temp_dir` selects scratch storage only, and temporary decompressed content
  is deleted after the operation;
- no `persist`, `cache_dir`, automatic persistent copy, or public unpack helper
  is introduced;
- callers who repeatedly use the snapshot own one explicit decompression and
  pass the resulting `.db`; and
- `write_parquet()` and the database-level unbounded eager
  `extract_mapping()` are removed from the stable v1 surface. Selected
  `EggNOGSelection.extract_mapping()` remains.

`from_sqlite()` detects gzip transport before expensive work and emits one
caller-actionable warning:

```python
warnings.warn(
    "Compressed eggNOG SQLite source detected. bioextract must fully "
    "decompress it to a temporary SQLite file before access, and the "
    "decompressed file is not persisted. Repeated use may repeat this cost; "
    "for long-term use, decompress the source once and pass the .db file.",
    UserWarning,
    stacklevel=2,
)
```

The library does not emit the same message through logging. `logger.warning()`
is reserved for operational events, and deprecated `logger.warn()` is not
used. No custom warning class is added until more than one resource needs a
stable, filterable performance-warning category.

The historical eggNOG 5.0.2 benchmark remains the evidence baseline: about
6.4 GB compressed input, about 41 GB temporary SQLite, 118,683,777 mapping
rows, and an old 949 MB Parquet publication. It is relabeled as a legacy
Parquet baseline rather than overwritten.

## GO Scientific Boundary

Remove the bioextract-specific subcell projection:

- `GODatabase.extract_subcell()`;
- `GODatabase.write_subcell()`;
- the derived `subcell_name` schema;
- the associated Parquet artifact and implementation helpers; and
- public examples and tests that promote the projection.

Callers use official GO `cellular_component` terms and ontology relations
directly. This removal does not affect UniProt curated subcellular-location
annotations, which are official UniProt domain relations.

## Compatibility And Migration

This is deliberate pre-1.0 convergence:

- no `write_parquet()` alias or deprecation period;
- no `write_tidy()` compatibility path;
- no metadata v1/v2/v3 reader matrix from the development period;
- no old `extract_subcell()` alias;
- no automatic conversion of existing artifacts; and
- no canonical publication in two formats.

Formal artifacts were rebuilt rather than treated as compatible because their
physical format or metadata contract changed. A legacy file that
reports an old metadata version or lacks the new required v1 keys is rejected,
even if its biological tables happen to resemble the current schema.

Direct official representations retain their upstream format and are not
rewritten for provenance consistency.

## Risks And Controls

| Risk | Control |
| --- | --- |
| A one-table DuckDB is materially larger or slower than the former Parquet | Record size, build time, scan, selected-ID query, and repeated-query benchmarks before formal replacement; retain the legacy benchmark for comparison |
| DuckDB unification accidentally turns every resource into a materialization job | Require an identified repeated-query, parsing, or distribution benefit before adding a writer; direct-only is a valid final capability |
| A capability-specific publication is reopened through the wrong resource path | Validate resource name, source schema profile, resource schema version, capability/table inventory, and required relations in `from_duckdb()` |
| Metadata version reset accepts an old development artifact also labeled v1 | Require the complete new v1 key and table contract; old v1 shapes fail validation |
| gzip warning becomes noisy or hidden | Emit one standard `UserWarning` at the public constructor boundary; do not duplicate it through logging |
| Real builds exhaust local disk, CPU, or process limits | Run one external snapshot build at a time, use explicit scratch roots, bound Polars/DuckDB workers through repository configuration, and check process cleanup after each build |
| Migration rewrites historical evidence | Mark old plans as superseded only for the affected storage scope and retain benchmark observations unchanged |

## Final Acceptance

The convergence is complete based on the landed code and tests and acceptance
of the nine formal publications above:

1. Current docs describe `official/native direct access` or
   `bioextract-owned DuckDB`, never a canonical single-relation Parquet rule.
2. No public `write_parquet()`, `write_tidy()`, GO subcell writer, or
   database-level eggNOG full eager extractor remains.
3. Every supported materialization capability writes one DuckDB and can reopen
   it through the owning `XDatabase.from_duckdb()`; optional writer capability
   does not imply a maintained formal publication.
4. Every reopened publication exposes a new read-only `connect()` connection
   and its documented domain selections.
5. Every supported publication contains metadata v1 and exactly the five
   `_bioextract` provenance tables with matching inventories and counts.
6. eggNOG plain SQLite remains warning-free; gzip input warns before expensive
   work and creates no persistent cache.
7. Grouped selections retain unique-ID resolution and group fan-out semantics.
8. The nine formal rebuilt files passed their publication validation; KEGG
   metabolic passed with its two documented validation issues.
9. Focused slice tests and the canonical non-mutating code gate passed during
   implementation delivery.

The resulting user model is intentionally small:

```text
official representation already fit for use
    -> XDatabase.from_<official_format>()

official representation requires stable materialization
    -> source.write_duckdb("tidy/data.duckdb")
    -> XDatabase.from_duckdb("tidy/data.duckdb")
```
